# 测试验证高级执行手册

本手册把“运行命令”和“验收对齐”合并为一条可追溯证据链。测试用例是重要证据，但不是天然高于已确认需求和技术方案的唯一真相。

## 1. 模式与证据门禁

先按用户目标选择最小交付模式：

| 模式 | 适用情况 | 最小交付 |
|---|---|---|
| 完整对齐验证 | 需求、方案、实现、用例均可读取，需要交付判断 | 完整主报告 |
| 失败定位 | 只有一个或少量失败项 | 单用例证据链、主分类、下一步 |
| 覆盖评审 | 已有测试结果，重点判断覆盖充分性 | 覆盖矩阵、缺口、建议 |
| 用例校准 | 用例预期与已确认口径冲突 | 口径差异、证据、待确认项 |
| 只运行测试 | 用户只要求执行具体命令 | 命令、退出码、通过/失败/跳过数 |

只有验收口径、可执行用例和实现路径/变更证据均可核对时，才能给出完整对齐结论。输入不足时记录缺口及最小补充材料，不生成假完整报告。

## 2. 能力探测与标准降级

开始前探测并记录：

- 代码、构建工具和测试脚本是否可读、可执行；
- 目标环境、服务地址、端口和依赖是否可用；
- 当前角色需要哪类 token、账号、权限或临时凭证；
- 测试数据、清理权限和外部依赖是否具备；
- API、数据库、Redis、MQ、ES、WebSocket 等验证通道是否可访问。

缺少环境时，仍可执行静态映射、本地编译和可用单测，并把环境链路标为 `阻塞` 或 `未验证`。缺少 token 时，只执行无登录态验证和静态契约核对，列出缺失角色及影响范围。以上都属于标准降级；不得伪造请求、响应、日志或通过结果，也不得给出通过结论。

凭证只记录是否存在、角色、权限范围和脱敏标识。不得在主产物、辅助产物、命令输出摘录或最终回复中写入完整 token、Cookie、Authorization、账号或密码。历史脚本中的凭证只能用于识别参数和角色，不能默认复用。

## 3. 测试资产优先级

按下列测试资产优先级选取验证方式，每次使用前都要检查默认环境、默认参数、写操作和凭证来源：

1. 当前需求已有的专项脚本；
2. 当前需求的联调说明和可执行步骤；
3. 历史报告中可复用的结构、断言和步骤；
4. 项目现有单测、集成测试和接口测试工具；
5. 基于真实 Controller、DTO、SQL 和配置编写的最小验证步骤。

不得因为已有脚本就跳过安全检查，也不得让历史报告替代本轮实际执行。

## 4. 环境、权限与前置数据

执行前形成环境与能力清单：

| 项目 | 当前值/状态 | 证据 | 影响 |
|---|---|---|---|
| 代码版本与 diff | | | |
| 运行环境/baseUrl | | | |
| 服务和依赖 | | | |
| token 角色与权限 | | | |
| 前置数据 | | | |
| 写数据影响与清理 | | | |

员工端、管理端、学生端或其他角色 token 不得混用。涉及写接口、状态变化或消息发送时，先确认数据影响、清理或最终状态回查方式；不得对线上环境执行写验证，除非用户明确授权并给出回滚方案。

用例的前置数据、操作步骤、预期结果和环境约束缺任一项时，先判定其可执行性，不能直接判实现错误。

## 5. 应测场景与映射

先建立场景清单，再执行：

| 场景 ID | 来源 | 场景 | 类型 | 验证方式 | 状态 | 证据 | 未测/阻塞原因 |
|---|---|---|---|---|---|---|---|

状态仅允许 `已验证`、`未验证`、`阻塞`、`不适用`。每个未测和不适用项都要说明原因，覆盖率百分比不能替代场景清单。

按本次改动风险覆盖编译、单测、主路径、边界、异常、权限、状态、幂等、兼容、批量性能、SQL、缓存和异步链路。并建立：

| 用例 ID | 预期 | 需求依据 | 方案依据 | 实现落点 | 实际结果 | 追溯结论 |
|---|---|---|---|---|---|---|

找不到需求依据的用例标为新增口径或待确认；需求明确但方案缺失优先判方案遗漏；不能为了让用例变绿而静默扩张业务边界。

## 6. JSON 入参和 Jackson 绑定

API 验证必须记录实际发送的请求方式、路径、Header 类型、Content-Type、脱敏请求体和响应，HTTP 200 不等于业务成功。

发送 JSON 入参前必须确认：

- 请求体是合法 JSON，字段名使用双引号；
- `Content-Type` 与接口契约一致；
- 数字、字符串、布尔、数组、对象和枚举与 `@RequestBody` DTO 类型一致；
- 前端禁止传字段和后端推导字段按契约验证；
- `zValue`、`pType`、`uId` 等 JavaBean 高风险字段通过显式 `@JsonProperty` 及 ObjectMapper/MVC 测试验证 Jackson 绑定，区分“未发送”和“未绑定”。

Windows PowerShell 中不得使用会破坏引号的手拼 curl JSON。优先使用项目脚本、BodyFile、原生对象序列化、HttpClient 或已验证的接口测试工具。出现 400、解析异常、字段全空或枚举绑定失败时，先检查真实请求体、Content-Type 和 DTO 映射。

## 7. 执行层级与原始证据

由低到高执行：

1. 相关模块编译；
2. 变更相关单测和集成测试；
3. API 契约与角色权限；
4. 业务主链路和状态回查；
5. SQL 条件、JOIN、分页、逻辑删除、索引风险和最终数据；
6. Redis、MQ、ES、WebSocket、定时任务等异步验证；
7. 旧接口、旧状态、空数据和历史数据回归；
8. 测试数据清理或最终状态确认。

批量场景禁止在循环中逐条查询数据库、RPC 或外部 API。聚合和映射异常时，追到响应最终赋值点，核对实体集来源与映射来源是否一致，不用 fallback 掩盖源头分裂。

每次实际执行都写原始执行记录：

| 时间 | 命令/步骤 | 环境 | 退出码/状态 | 关键输出 | 证据位置 |
|---|---|---|---|---|---|

失败记录必须包含直接失败点、请求/输入、实际响应或错误、最终数据源/计算点、关键参数和下一验证动作。未执行的动作不得写成已验证。

## 8. 六类差异归因

每个差异先选择一个主分类：

| 分类 | 判断依据 | 处理方向 |
|---|---|---|
| 需求歧义 | 预期无明确依据或需求冲突 | 回到需求澄清 |
| 方案遗漏 | 需求明确但方案未覆盖或口径错误 | 更新方案并评审 |
| 实现偏差 | 需求和方案明确，实现链路未兑现 | 最小代码修复 |
| 测试用例偏差 | 需求、方案、实现一致，用例预期不一致 | 校准用例 |
| 环境/数据问题 | 配置、权限、缓存、依赖或前置数据不满足 | 修复环境/数据 |
| 覆盖不足 | 关键需求或风险没有证据 | 补充用例和执行 |

结论证据链应包含：失败点、需求依据、方案依据、实现路径、最终数据源/计算点、关键参数、测试证据、主分类。守卫条件和字段非空检查不自动等于真实业务依赖。

## 9. 测试轮次与产物权威

`06-test-report.md` 或 `03-test-report.md` 始终是当前阶段唯一权威主产物。每次测试更新主产物中的当前结论、场景状态、未关闭缺口和轮次索引。

需要保留详细历史时，在同一特性目录下新增 `auxiliary/test-rounds/test-rNN.md`。测试轮次只能追加，不能覆盖旧轮次；修复后复测也新增下一轮。辅助报告、API 报告、日志摘要和 SQL 回查路径必须由主产物索引，不能形成第二份当前结论。

## 10. 结论门禁

- `建议交付`：所有关键场景有通过证据，六类差异无阻塞，覆盖风险可接受；
- `有条件交付`：仅有明确的低风险缺口，并列出 Owner、补测、监控或回滚条件；
- `暂缓交付`：存在实现偏差、方案遗漏、高影响歧义、关键失败、关键未测或不可信环境；
- `无法判断`：需求、方案、实现或测试事实不足以形成闭环。

环境、token、权限、前置数据或外部依赖缺失导致关键场景无法执行时，不得给出通过或建议交付。测试阶段默认只报告和归因；用户没有明确要求修复时，不修改业务代码。
