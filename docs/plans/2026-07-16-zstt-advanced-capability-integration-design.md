# ZSTT 高级能力融合设计

> 历史设计记录：高级能力仍被保留，但共享协议和 Java 团队规范在 0.2.0 中已迁移到 `.zstt-kit/rules/`，当前路径以能力矩阵为准。

## 1. 背景

ZSTT Backend Workflow 已完成首版统一，具备 quick/full 双轨、七个显式阶段 Skill、`.zstt/` 产物目录、单阶段单主产物、P0 门禁、上游重新校验和确定性 CLI。

首版重点解决流程统一和阶段契约，因此将 `agent-skills` 与 `ggg-backend-skills` 中较长的操作细节压缩成核心规则。下一版本需要恢复两套来源项目已经验证过的高级能力，但不能破坏用户已经确认的工作方式。

## 2. 目标

- 完整盘点两个来源项目的高级能力，并为每项能力确定迁移位置或排除理由。
- 保留需求澄清、跨仓库调研、技术方案、任务拆分、实现、Review、测试和代码简化的深度操作方法。
- 采用渐进加载，避免把数百行规则全部堆入阶段 `SKILL.md`。
- 对 CodeGraph、远程仓库 MCP、token、测试环境和并行执行等能力进行探测，有能力时增强、无能力时降级。
- 保持现有 `.zstt` 路径、阶段顺序、主产物编号和用户显式选择规则兼容。
- 为新增能力补充契约测试、场景评测和端到端回归验证。

## 3. 不变约束

- 用户必须显式调用具体阶段 Skill。
- Skill 只执行当前阶段，结束后只能推荐下一阶段，不能自动执行。
- 每个阶段只有一份权威主产物；辅助文件不能与主产物争夺权威性。
- 用户可以修改任何阶段产物；下游开始前必须重新校验上游。
- P0 阻塞时不创建或完成下游产物。
- quick/full 目录和固定编号保持不变。
- 工作流止于测试验证，不自动 commit、push、合并、发布或部署。
- 首版技术栈仍限定为 Codex 和 Java 后端。

## 4. 方案选择

### 4.1 方案一：全文复制并改名

优点是来源能力保留直观；缺点是重复规则多、旧目录和自动推进语义容易残留，阶段 Skill 会过长，维护时无法判断哪份规则是权威来源。

### 4.2 方案二：阶段主文件加高级参考（采用）

阶段 `SKILL.md` 保留触发、主流程、硬门禁和产物契约；每个阶段使用自己的 `references/advanced-playbook.md` 保存高级方法、检查清单、工具路径和异常处理。共享底座只保留真正跨阶段的协议。

这种结构能保留原能力，同时符合 Codex Skill 的渐进加载原则，并能通过测试确保主文件确实在需要时加载高级参考。

### 4.3 方案三：统一大型共享知识库

优点是重复最少；缺点是阶段需要从大文档中筛选规则，容易读取无关内容，需求澄清、技术方案和测试验证之间的职责边界会变弱。

## 5. 分层架构

```text
用户显式调用阶段 Skill
  -> 阶段 SKILL.md：触发、边界、主流程、门禁、主产物
  -> 阶段 advanced-playbook.md：高级分析与执行方法
  -> workflow-shared：能力探测、证据、文档权威、状态协议
  -> 可用工具增强路径 / 标准降级路径
  -> 当前阶段主产物 + 可选辅助证据
```

### 5.1 阶段 SKILL.md

每个主文件保持可快速加载，负责：

- 明确何时触发和不得隐式触发；
- 读取共享协议和当前阶段高级参考；
- 执行当前阶段的固定顺序；
- 调用 CLI 校验和完成阶段；
- 输出主产物路径、风险和下一阶段建议。

### 5.2 阶段高级参考

每个固定阶段和代码简化 Skill 增加 `references/advanced-playbook.md`。参考文件负责：

- 来源项目中的高级操作步骤；
- 输入盘点和质量检查清单；
- 可选工具探测与使用策略；
- 标准降级路径；
- 事实、推断、风险和未知的记录方式；
- 用户纠正、失败和重试的处理方式。

### 5.3 共享底座

共享底座新增或加强以下跨阶段协议：

- 能力探测与降级规则；
- 文档权威和辅助附件规则；
- 证据等级与 Claim Ledger 最小结构；
- 用户纠正和上游回写规则；
- 可选并行执行的安全边界；
- 工具使用、失败边界和未验证事实的记录格式。

## 6. 能力迁移映射

### 6.1 需求澄清

融合 `prd-clarifier` 和 `ggg-prd-intake`：

- 盘点 PRD、PDF、网页、截图、流程图、时序图和表格等混合输入；
- 区分直接澄清、局部补充和已有文档审阅；
- 先建立文档骨架，再逐轮回写；
- 扫描同一材料内部和多份材料之间的冲突；
- 区分原始事实、整理归纳、推断、冲突和未确认；
- 执行 P0/P1/P2 分级、多轮澄清和确认日志；
- 对非文本材料记录可读范围和无法识别内容；
- 保留 quick/full 模式分流，但不替用户选择。

### 6.2 仓库调研

融合 `clarified-requirement-repo-research` 和 `ggg-requirement-alignment`：

- 先确认仓库边界和主项目，再建立代码验证清单；
- 远程仓库读取、CodeGraph、本地 checkout 按能力探测选择；
- 使用 CodeGraph 时检查目标项目和索引新鲜度；
- 从真实入口追踪 Service、Facade、Client、Repository、Mapper、SQL 和异步链路；
- 强制检查旧链路副作用和跨仓库契约；
- 按仓库输出需改清单和每仓库变更范围；
- 使用 Claim Ledger 记录结论、证据、置信度、反证和待验证动作；
- 区分静态证明、框架推断、需求声明、运行时依赖和未知。

### 6.3 技术方案

融合 `writing-backend-technical-solutions` 和 `ggg-technical-design`：

- 建立当前代码基线、目标差距和设计输入清单；
- 对高影响歧义设置设计前确认点；
- 设计数据身份、状态、职责、存储、索引、事务、缓存和异步；
- 展开接口请求、响应、错误码、幂等、权限、兼容和 Jackson 约束；
- 给出真实代码落点和跨仓库发布顺序；
- 使用 Mermaid 绘制必要的业务流程、时序和架构关系，不用图替代文字契约；
- 记录架构取舍、候选方案、未采用理由和验证方式；
- 覆盖灰度、监控、发布、回滚、数据迁移和测试策略。

### 6.4 任务拆分

融合 `ggg-task-breakdown`：

- 建立需求、调研、方案到任务的完整覆盖矩阵；
- 每个任务包含来源、文件范围、接口/SQL/配置范围、依赖和完成标准；
- 标记关键路径、阻塞点、并行等级和冲突文件；
- 映射接口、数据、兼容、发布和测试工作；
- 提供精确验证命令和预期信号；
- 不按 Controller、Service、Mapper 机械切分不能独立闭环的任务。

### 6.5 编码实现

融合 `ggg-implementation` 和团队 Java 规则：

- 执行门禁、范围冻结、Git 状态检查和任务状态同步；
- 从代码事实确认落点，建立失败测试或可复现失败信号；
- 设计最小实现顺序，按任务或安全并行组执行；
- 能力允许且当前任务确实独立时，可在当前阶段启用 Codex 子任务；
- 并行任务不得修改同一文件、接口契约、Mapper XML、SQL 或共享配置；
- 每组完成后先验证再汇总，不把子任务声明直接视为事实；
- 发现需求或方案偏差时停止并回写上游；
- 保留 N+1、Jackson、注释、数据源一致性和 smart-doc 等团队硬门禁。

### 6.6 代码评审

融合 `ggg-code-review`：

- 冻结基线、工作区、diff、未跟踪业务文件和评审范围；
- 建立需求、方案、任务、实现和测试一致性矩阵；
- 执行真实调用链复核和幻觉审计；
- 能力允许时按业务正确性、数据/并发、接口兼容、性能、安全和测试分路只读审查；
- 汇总时去重、验证代码位置和失败条件，不直接相信并行审查结论；
- 支持 Review 轮次和修复后的复审，但主结论必须回写主产物；
- 默认只读，用户明确要求修复时仍先完成当前轮评审。

### 6.7 测试验证

融合 `verify-implementation-with-test-cases` 和 `ggg-test-verify`：

- 建立测试资产优先级和应测场景清单；
- 检查环境、token、权限、依赖服务、配置、缓存和前置数据；
- 对 JSON 请求检查字段名、类型、枚举、必填、默认值和 Jackson 绑定；
- 执行编译、单测、接口、主链路、SQL、异步和回归验证；
- 保存执行命令、输入摘要、退出码、关键结果和时间；
- 将差异分类为需求歧义、方案遗漏、实现偏差、用例偏差、环境/数据问题或覆盖不足；
- 支持测试轮次和缺陷回归，但最终结论只写入当前主报告。

### 6.8 代码简化

完整融合 `code-simplification-refactor`：

- 按用户指定范围、提交范围、当前 diff 或最新提交确定边界；
- 从复用、简化、效率和抽象层级四路审查；
- 能力允许时可以并行分析，但修改由主上下文统一验证和应用；
- 只应用行为保持且证据充分的安全清理；
- 保持接口、数据范围、异常、调用顺序、事务和并发语义不变；
- 使用相同验证信号比较修改前后行为。

## 7. 能力探测与降级

阶段开始时只探测与当前任务相关的能力，不安装、不假设存在：

| 增强能力 | 可用时 | 不可用时 |
|---|---|---|
| 远程仓库 MCP | 远程只读搜索和取证 | 使用用户提供的本地 checkout |
| CodeGraph | 结构化调用关系和索引查询 | 使用 `rg`、IDE 索引和逐层源码追踪 |
| PDF/图片/网页读取 | 提取非文本需求证据 | 记录不可读范围并请求补充文本 |
| Codex 子任务 | 对独立任务或只读专项并行处理 | 主上下文串行执行 |
| API/token/测试环境 | 执行真实接口和链路验证 | 执行本地单测、编译和静态核对，明确未验证范围 |

所有路径都必须记录：探测结果、实际使用工具、失败边界、降级方式和证据置信度。工具不存在本身不是业务阻塞，但如果缺少它导致关键事实无法证明，必须形成 P0 或开放风险。

## 8. 产物与附件

主产物编号和路径不变。高级细节可以进入 `auxiliary/`：

- `claim-ledger.md`；
- `interface-details/`；
- `schema.sql` 或 SQL 草案；
- `review-rounds/`；
- `test-runs/`；
- `tool-capabilities.md`。

附件只保存详细证据和可复用材料。主产物必须包含附件索引、关键结论和当前权威状态。发现冲突时以主产物为准，并同步修正附件。

## 9. 错误和纠正处理

- 用户纠正需求或代码事实时，立即更新当前结论并识别受影响的上游主产物。
- 下游发现上游冲突时停止当前阶段，不在下游增加 fallback 掩盖问题。
- 工具失败时记录尝试和边界，切换标准降级路径；不能把失败调用写成验证成功。
- 并行子任务失败不影响其他安全任务，但主上下文必须验证全部合并结论。
- 运行时条件无法证明时标记为 Runtime dependent 或 Unknown，并给出验证动作。
- 阶段失败不推进 `meta.json`，也不创建伪完成的后续产物。

## 10. 测试与评测

### 10.1 契约测试

- 每个阶段 `SKILL.md` 必须读取自己的高级参考；
- 高级参考覆盖能力映射中的必需关键词和行为；
- 可选工具必须同时定义增强和降级路径；
- 并行能力不得自动推进阶段或绕过主上下文验证；
- 辅助文件不得改变主产物权威性；
- 所有文本保持 UTF-8 无 BOM，`SKILL.md` 控制在 500 行内。

### 10.2 场景评测

评测至少覆盖：

- 含截图和冲突描述的正式需求；
- CodeGraph 不可用的跨仓库调研；
- 涉及接口、SQL、状态和历史兼容的方案；
- 存在共享文件冲突的任务并行判断；
- 实现与方案不一致时的上游回写；
- Review 中的幻觉审计和复审轮次；
- token 或环境缺失时的测试降级；
- 代码简化中高风险建议的跳过。

### 10.3 回归验证

- 现有 42 项测试全部通过；
- 新增高级能力契约测试通过；
- full/quick 端到端流程保持兼容；
- Python 编译、Git diff 检查和 UTF-8 BOM 检查通过。

## 11. 完成标准

- 两个来源项目的高级能力都有迁移位置或排除理由；
- 每个阶段主文件和高级参考职责清晰；
- 工具存在和不存在两种路径都可执行；
- 不恢复自动串行、自动推进或自动发布；
- `.zstt` 目录和现有产物兼容；
- 新增规则有测试和代表性评测用例；
- README 能说明高级能力、降级方式和附件边界。
