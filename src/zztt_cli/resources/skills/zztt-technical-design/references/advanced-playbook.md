# 高级后端技术方案 Playbook

## 1. 方案目标

把已澄清需求和已验证代码事实转换成可评审、可拆任务、可验证的 Java 后端技术方案。方案必须同时回答：当前后端真实如何运行、目标需求与现状差什么、为什么选择当前改造、具体改哪里、怎样发布和证明正确。

`00-requirement.md` 提供目标口径，`01-research.md` 提供代码事实和 Claim Ledger。设计不能把目标写成现状，也不能把字段存在、Guard 非空判断或局部查询结果直接推断成业务语义。

## 2. 设计输入清单

盘点实际存在的输入并说明用途：

- 需求主产物、原始 PRD 和用户确认记录；
- 调研主产物、Claim Ledger、仓库和运行时缺口；
- 当前分支/HEAD、相关模块、接口、DTO、表、SQL、配置和消息；
- 用户提供的计划、任务、契约或数据模型材料；
- 当前项目 `AGENTS.md` 和 Java 团队规范。

缺少非必需补充材料不自动阻塞。只有会改变状态、接口契约、数据身份、统计口径、上下游职责、存储或发布兼容的缺口才升级为高影响歧义。

## 3. 设计预检与高影响歧义

开始正文前完成：

1. 当前代码基线；
2. 需求与现状差距；
3. 数据身份、去重维度、状态隔离和生命周期；
4. 页面/调用动作到后端接口的协作骨架；
5. MySQL、Redis、ES、MQ、配置和计算结果的数据承载选择；
6. 影响方案定稿的 P0 和运行时缺口。

高影响歧义包括状态机、接口请求/响应、轮询/WebSocket/SSE/MQ 语义、数据归属、统计口径、DDL/SQL、兼容策略和上下游职责。存在时停止定稿，回写上游或发起一个单点确认：

```markdown
当前观察：基于需求或代码的可引用事实
影响点：会改变哪些章节、契约、SQL、发布或测试
候选方案：当前真正可行的 1–3 个选项
推荐方案：推荐理由、约束和代价
待确认问题：一个可直接回答的决策
```

用户催促交稿不能把 P0 变成事实。可以输出标注“评审草案/非最终稿”的方向性内容，但不得设置 `status: completed`。

## 4. 当前代码基线与差距

当前代码基线至少落到真实仓库、分支/提交、入口、Service/Facade、数据访问、表/SQL、配置、缓存、消息或任务。记录调研结论 `Cxx` 和证据位置。

差距按能力写：

```markdown
| 差距 ID | 模块 | 当前代码事实 | 目标需求 | 来源 Cxx | 结论/阻塞 |
|---|---|---|---|---|---|
```

重点检查状态/规则、接口、数据模型、查询统计、异步、任务、权限、安全和兼容差距。未由证据证明的“当前支持”必须改为方案建议或待确认。

## 5. 身份、职责与契约骨架

### 5.1 数据身份

```markdown
| 业务对象 | 唯一标识 | 去重维度 | 状态隔离 | 生命周期 | 身份来源 | 前端可传 | 来源 Cxx |
|---|---|---|---|---|---|---|---|
```

前端不应控制的用户、租户、当前实例和状态身份由后端从可信上下文推导。学生、教师、操作者和创建人不能都用含糊的 `userId` 语义代替。

### 5.2 职责边界

明确写入方、只读方、状态拥有者、计算拥有者和跨仓库契约。业务模块不能穿透修改其他模块表、Mapper、缓存 key 或内部实现。

### 5.3 接口协作骨架

```markdown
| 页面/动作 | 接口 | 首屏/点击后 | 请求关键字段 | 后端推导 | 前端禁止传 | 返回粒度 | 来源 Cxx |
|---|---|---|---|---|---|---|---|
```

查询和写入按业务动作拆分，避免把预览、提交、反馈和重查询塞入一个大接口。

## 6. 候选方案与设计决策

真实取舍至少比较两个可行候选方案。每项记录：

```markdown
| 设计 ID | 决策点 | 候选方案 | 选择 | 未采用理由 | 来源 Cxx | 边界/代价 | 验证方式 |
|---|---|---|---|---|---|---|---|
```

设计决策用 `Dxx`，必须引用 Claim Ledger 中存在的 `Cxx`。没有来源结论时先回写需求或调研，不用“经验做法”伪造证据。

按场景评估设计模式、缓存、锁、幂等、并发、异步化、新技术和中间件。只有存在真实变化点或风险才展开；推荐模式时写清解决的变化点、不使用的代价和最小实现。不要为单次使用引入策略、工厂、状态机或配置平台。

## 7. 图表与实现映射

每张 Mermaid 图只回答一个问题：

- 整体架构图：系统边界、分层和主依赖方向；
- 改造落点图：哪些模块保持、修改或新增；
- 关键流程图：从真实触发点开始怎样运行；
- 时序图：一次业务交互如何跨参与方发生；
- ER 图：表和逻辑关联。

不要把业务流程、字段、表关系和模块分层塞入同一张图。

统一颜色：原逻辑蓝色、变更点橙色、新增点绿色。流程图决策节点使用 `{}` 并标出口条件，异常/补偿/异步使用虚线或独立路径。节点超过 10 个或关键分支超过 3 个时拆图。

时序图 participant 使用前端、业务能力、依赖服务、Redis、数据库、MQ 等交互角色，不堆 Controller/Service/Mapper 类名；类和方法写在图下“实现映射”。同步、返回、异步、`alt`、`opt`、`loop` 语义必须正确。

无法从代码可靠还原时不画占位图，改为列出已确认链路、缺失链路和阻塞点。

## 8. 接口明细

每个新增或变更接口必须可直接评审：

- 路径/RPC 方法和调用方式；
- 当前状态、本次改造和来源 `Cxx/Dxx`；
- 请求/响应字段、类型、必填、默认值、枚举和值域；
- 错误码、异常语义和业务成功判断；
- 权限、租户、角色、数据范围和敏感字段；
- 幂等、重复提交、并发和状态隔离；
- Jackson 高风险字段的 `@JsonProperty` 和绑定测试；
- 兼容、灰度、版本策略和代码落点；
- JSON 示例、流程和测试链路。

详细接口可以放 `auxiliary/interface-details/`，但 `02-design.md` 必须保留契约总表、关键字段、最终决定和附件索引。附件不是第二份权威方案。

## 9. 数据存储与查询设计

### 9.1 数据承载

```markdown
| 数据/状态 | MySQL | Redis | ES | MQ | 配置/计算 | 选择原因 | 一致性/过期/失败策略 |
|---|---|---|---|---|---|---|---|
```

- MySQL 承载长期业务事实、关系和审计；
- Redis 承载短期状态、热点缓存或锁，必须写 TTL、一致性和击穿处理；
- ES 服务搜索和聚合，不默认成为唯一业务真相；
- MQ 承载异步事件和同步，必须写幂等键、重试、顺序、重复和死信；
- 配置写默认值、刷新、灰度和回滚。

### 9.2 表和字段准入

每张表和字段说明业务事实、写入事件、查询场景、生命周期、是否可推导和不落库后果。仅为“以后可能用”或排查方便的字段不落库；冗余必须说明一致性风险。

表名、公共字段和索引风格优先参考同模块既有表、Entity、Mapper 和 SQL。没有证据时标为待确认，不自造命名体系。`user_id` 不是默认公共字段，必须证明业务语义、来源和隔离需求。

### 9.3 查询、索引和事务

- 明确查询条件、分页、排序、统计和逻辑删除/租户范围；
- 禁止 N+1 和循环单 ID 远程调用；
- 索引根据真实查询和选择性设计，说明写放大和维护代价；
- 事务边界围绕一致性，不把无依据的慢远程调用放入事务；
- 缓存、DB、MQ 的提交顺序、失败补偿和幂等闭环必须具体。

### 9.4 数据迁移

说明历史数据默认值、回填范围、批次、限速、校验、双读/双写、兼容窗口、失败重试和回滚。无数据迁移也要写原因。

详细 DDL/SQL 可写入 `auxiliary/schema.sql`，主方案必须包含表/字段/索引摘要、准入结论和确认状态。SQL 评审属于当前技术方案阶段，不新增自动阶段或竞争性编号产物。

## 10. 扩展性与维护性

把要求映射到真实变化点：职责归属、变化点隔离、依赖方向、数据访问边界、契约稳定、可测试性、适度配置化、可观测性和演进路径。

```markdown
| 要求 | 具体落点 | 解决的变化/耦合风险 | 不采用的代价 | 验证方式 |
|---|---|---|---|---|
```

禁止只写 SOLID、高内聚低耦合或方便扩展。若不引入新模式，写清如何通过边界收口、命名、注释和测试保持可维护。

## 11. 性能、安全与质量

只展开当前场景相关项，但相关时必须写风险来源、当前基线、候选方案、推荐、约束和验证方式：

- 性能：批量查询、N+1、容量、分页、缓存命中、慢 SQL、内存和 GC；
- 安全：认证、授权、越权、租户隔离、敏感数据、注入和审计；
- 质量：并发正确性、锁、线程安全、幂等、超时重试、资源释放和失败隔离；
- 可观测：业务身份、规则命中、耗时、错误、消息、补偿、指标和 Trace；
- 可测试：主链、边界、兼容、异步、并发和回归验证。

不要写“注意性能/加强安全”。每项必须有发现方式和可执行验证。

## 12. 发布、灰度、监控与回滚

写清跨仓库发布顺序、数据库/配置/消息兼容窗口、灰度开关、老接口和老数据兼容、监控指标、告警阈值、停止条件和回滚步骤。

回滚必须说明：应用回滚后新增字段/消息/缓存如何处理，是否需要停任务、关闭开关、回滚数据或保留兼容读。不能只写“回滚版本”。

## 13. 风险和完成检查

- 当前代码基线和目标需求严格分开；
- 每个 `Dxx` 可追溯到 `Cxx`，并记录候选方案和未采用理由；
- 身份、状态、职责、接口、存储和数据迁移已闭环；
- Mermaid 图各司其职且有实现映射；
- 接口明细包含错误码、权限、幂等和兼容；
- 查询、索引、事务、缓存、MQ 和历史数据有可执行口径；
- 扩展性与维护性以及相关的性能、安全与质量要求可评审；
- 灰度、监控、发布和回滚可执行；
- 附件索引完整，主产物保留最终结论；
- 高影响歧义已上游回写或保持 P0，不能以最终方案完成阶段。
