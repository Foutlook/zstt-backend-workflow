# 高级编码实现 Playbook

## 1. 目标与权威输入

在当前实现阶段内，按已确认范围完成最小、可验证的代码闭环。full 以 `03-tasks.md` 为执行看板，结合需求、调研、方案和辅助附件；quick 以 `00-requirement.md` 和 `01-implementation.md` 中的简短计划为边界。

真实代码事实优先于文档中的类名或旧落点，但业务口径、接口契约、表结构、状态、发布风险发生变化时必须停止并上游回写，不能以“代码现在这样”替用户改变方案。

## 2. 门禁与范围冻结

开始前：

1. 运行 `prepare-stage --stage implementation`；
2. 读取项目 `AGENTS.md`、Java 团队规范和当前阶段主产物；
3. 执行 `git status --short`，识别用户已有改动、未跟踪文件和当前基线；
4. full 只选择依赖已满足的 ready 任务；quick 复述目标、改什么、不改什么和验收信号；
5. 固定本轮仓库、任务、预计文件、接口/SQL/配置范围和验证方式；
6. 相关文件存在未理解改动时先读懂，不覆盖、不回滚。

范围冻结记录：

```markdown
| 任务 | 允许修改 | 只读参考 | 明确不改 | 用户已有改动 | 验证方式 |
|---|---|---|---|---|---|
```

任务状态只执行 ready。开始后记录 in_progress，完成并通过验证后记录 done；依赖或口径无法满足时记录 blocked 和解除条件。

## 3. 代码事实定位

从任务中的入口、类、方法、表、接口和符号定向搜索，按入口、Service/Manager、Facade/Client、Repository/Mapper/SQL、DTO/枚举/配置、测试的顺序确认真实落点。

语义索引或 CodeGraph 可用时先检查目标子项目和 pending 状态；不可用时用 `rg`、`rg --files`、构建文件和逐层源码读取。任何工具“未找到”都只表示当前证据未覆盖，不能证明代码不存在。

定位结束后更新范围冻结。发现需要修改范围外文件时，先判断是否是漏列的同一闭环，还是会改变任务/方案；后者必须暂停。

## 4. 失败信号和最小实现顺序

每个任务开始前建立失败信号：失败单测、可复现命令、编译错误、接口响应、SQL 结果或明确静态契约检查。记录命令、退出码和关键输出，避免“凭感觉已修”。

选择最清楚的最小实现顺序，不机械套分层。常见顺序为：

1. 锁定接口、SQL、消息或配置契约；
2. 建立失败测试或可复现信号；
3. 修改实体/DTO/枚举/Mapper 等基础层；
4. 修改核心 Service/Manager/Facade 主链；
5. 接入 Controller/Job/MQ/RPC 入口；
6. 运行局部验证并记录结果；
7. 完成一个闭环后再开始下一任务。

主方法优先呈现校验、查询、计算、写入、通知和返回等业务步骤。复杂细节只在确实提高可读性或复用时抽取，不引入无效 Helper、万能 Manager 或单实现模式层。

## 5. Java 实现质量

同时执行动态解析得到的 Java 规则：

- Controller 薄，Service/Facade 主链清晰；
- 禁止 N+1、循环查库、循环远程调用、循环写库和 `SELECT *`；
- 列表场景批量收集参数，再批量查询/调用并内存映射；
- SQL 明确逻辑删除、租户、权限、分页和稳定排序；
- 高风险 Jackson 字段显式 `@JsonProperty`，需要真实兼容时才用 `@JsonAlias` 并补绑定测试；
- 保留既有注释，复杂状态、顺序、事务、异步、幂等和兜底解释原因；
- 异常保留堆栈和业务上下文，不泄露 token、Cookie、密码或敏感数据；
- 事务不无依据包裹慢远程调用，DB/缓存/MQ 顺序和补偿明确；
- 日志覆盖业务身份、状态变化、外部调用和最终结果，避免大对象和循环高频日志；
- 不为套规范重写无关历史代码。

## 6. 并行安全评估

`03-tasks.md` 的并行组只是候选。执行前按真实文件重新评估：

```markdown
| 任务 | 预计写入 | 共享依赖 | 契约/表/配置影响 | 冲突文件 | 结论 | 执行方式 |
|---|---|---|---|---|---|---|
```

不同仓库/模块/文件且只依赖稳定契约的任务才可并行。以下必须串行：

- 同一 Java 文件、Service 主链或测试基类；
- 同一 Mapper XML、SQL、配置或缓存 key；
- 同一接口详情、DTO 契约或消息体；
- Provider/Consumer、生产/消费两端契约未锁定；
- 表结构未确认，或一个任务依赖另一个未完成输出。

## 7. 可选 Codex 子任务

只有用户明确要求或批准当前实现阶段使用并行，任务为 L2 且当前环境支持时，才启用 Codex 子任务。并行只属于当前实现阶段，不改变 `prepare-stage`、`complete-stage` 和用户显式调用规则。

主上下文先建立写入锁：

```markdown
| 子任务 | 任务 | 允许修改 | 禁止修改 | 只读参考 | 依赖 | 合并顺序 | 局部验证 |
|---|---|---|---|---|---|---|---|
```

规则：

- 同一文件只交给一个子任务，目录级权限仅用于唯一命名空间下的新增文件；
- 子任务发现需要修改范围外、接口、SQL 或业务口径时必须停止；
- 每个子任务只处理一个清晰任务包并返回实际文件、验证和风险；
- 主上下文不重复修改被锁文件，但可以准备不重叠验证；
- 工具不支持、写集冲突或任务太小时自动走串行标准降级。

子任务返回后必须主上下文复核：检查实际文件是否越界、阅读完整 diff、验证契约、按顺序合并并运行组级验证。子任务的“已完成”不是最终事实。

Codex 子任务不得自动执行下一阶段、修改 `meta.json`、commit、push、合并分支或部署。

## 8. 分组验证

每个任务先局部验证，每个安全组再集成验证：

- 基础层：编译、字段/签名、Mapper 和 SQL 检查；
- 主链：聚焦单测、状态/异常/权限边界；
- 接口：请求/响应、Jackson、后端推导字段和兼容；
- 异步：消息字段、幂等、重复、乱序、重试、日志和补偿；
- 数据：批量行为、N+1、索引、分页和数据源一致性。

记录命令、退出码、关键输出、覆盖范围和未验证风险。验证失败时定位本轮最小改动，不使用破坏性 Git 命令清空用户工作。

Maven 项目中 smart-doc 绑定早期生命周期时，业务编译/单测使用 `-Dsmart-doc.phase=verify`；专门验证 API 文档时才按项目默认生命周期执行。

## 9. 偏差与上游回写

- 目标、范围、权限或验收改变：回写需求；
- 仓库、调用链、数据源或复用结论改变：回写调研；
- 接口、SQL、状态、事务、兼容、发布或回滚改变：回写方案；
- 文件范围、依赖、并行或验证改变：回写任务。

不影响业务口径的类名或局部分层偏差可按当前代码最小适配，但必须记录。回写后重新校验上游再继续，不能只在最终回复口头说明。

## 10. 实现记录与完成

主产物记录范围冻结、失败信号、任务状态、实际文件、执行方式、偏差回写、质量自检、分组验证和剩余风险。启用子任务时记录写入锁、实际修改、越界检查和合并顺序。

完成前：

1. 检查每个任务有输出物和验证信号；
2. 检查用户改动、注释、日志、异常、N+1、Jackson、权限、事务和兼容；
3. 运行 `complete-stage --stage implementation`；
4. 只推荐 `$zstt-code-review`，不得自动执行下一阶段；
5. 不自动 commit、push、合并或部署。
