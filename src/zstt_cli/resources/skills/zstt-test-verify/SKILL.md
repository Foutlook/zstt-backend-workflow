# ZSTT Test Verify

## 定位

验证实现是否满足已确认目标，并判断差异究竟来自哪里。测试用例是证据，不自动等同于需求真相。

仅当用户明确指定本 Skill 时执行。完成后流程止于交付结论，不得自动执行推荐的下一阶段，也不自动 commit、push、合并或部署。

## 开始前

1. 运行 `python .zstt-kit/runtime/rule_resolver.py resolve --skill zstt-test-verify`。
2. 以 UTF-8 完整读取解析结果中每个规则的 `path`，记录 `rulesetVersion`、`rulesetFingerprint`、规则 ID 和选择原因。解析失败或规则缺失时停止，并执行 `zstt check --here`。
3. 完整读取 `references/advanced-playbook.md`，按其中的模式分流、能力探测、凭证安全、执行证据和差异归因规则工作。
4. 盘点需求、方案、实现、测试用例、缺陷、环境、数据和运行证据；根据测试对象的真实接口、数据源和运行边界追加 `jackson`、`data-access`、`transaction`、`concurrency` 或 `smart-doc` 等上下文并重新解析。
5. 用户显式给出的需求目录优先；未给目录时运行 `current --repo-root <业务仓库>`，仅接受当前 Git 分支上的唯一未完成需求。0 个或多个候选时运行 `list --repo-root <业务仓库>` 展示候选并要求用户选择，禁止按日期猜测。
6. 运行 `python .zstt-kit/runtime/workflow_cli.py prepare-stage --stage test_verify --feature-dir <需求目录>`，重新校验必需上游。quick 可以不执行 Review；Review 产物一旦存在就必须通过校验。

## 验证模式

1. 按用户目标选择完整对齐验证、失败定位、覆盖评审、用例校准或只运行测试；full/quick 只决定主产物文件名，不决定验证深度。
2. 完整对齐验证覆盖全部需求场景并形成交付判断；失败定位只追当前失败到最终数据源/计算点及受影响链路；覆盖评审和用例校准不扩大为全量重测。
3. 失败定位至少记录单用例输入、直接失败点、实际结果、需求/方案/实现依据、关键参数、六类主分类和下一验证动作。
4. 无论采用哪种模式，都把当前结论、场景状态、未覆盖项和原始证据索引回写唯一主报告；详细日志或轮次可以进入 `auxiliary/test-rounds/`，不得只留在聊天或附件。
5. 失败涉及接口契约、SQL 数据范围、权限、核心状态或异步通道时，只扩展受影响链路并说明原因；无法形成完整交付判断时保持局部结论，不伪装成全量验证。

## 验证顺序

1. 先列应测场景，覆盖主路径、边界、异常、权限、状态、兼容、批量性能和异步链路。
2. 检查每个用例的前置数据、操作步骤、可断言预期和环境约束。
3. 建立需求、方案、实现和测试用例映射。
4. 对失败或高风险项追到直接失败点、真实调用链、最终数据源/计算点和关键参数。
5. 执行与风险相称的编译、单测、接口、主链路、SQL、异步和回归验证。
6. 每个未测场景写明原因；关键场景失败或未测时不得给出“通过”。

测试前先探测实际可用环境、token 角色、权限、前置数据和测试资产。工具或运行条件缺失时执行标准降级，保留未验证边界，不得伪造测试结果。

## 差异分类

每个差异先归入一个主类：

- 需求歧义：预期缺少明确需求依据或需求互相冲突；
- 方案遗漏：需求明确但方案未覆盖；
- 实现偏差：需求和方案明确，代码未按方案执行；
- 测试用例偏差：需求、方案、实现一致，但用例预期不一致；
- 环境/数据问题：配置、权限、缓存、依赖或前置数据不满足；
- 覆盖不足：关键需求或风险没有测试证据。

不要看到失败就增加 fallback、替代字段或兼容分支。先证明真实业务依赖和最终数据源。

## 状态与结论口径

- `阻塞` 表示缺少执行前提或门禁未通过；对应场景的验证结果仍写 `未验证`，并记录阻塞原因、影响和解锁条件，两者不得混用成通过状态。
- 同一失败事件存在独立证据断点时拆成多个差异 ID，每个差异只选一个主分类；相同根因不得为凑分类重复建项。
- 已有足够证据证明关键失败、关键阻塞或高风险未测时写“暂缓交付”；需求、方案、实现或测试事实不足到无法判断预期与风险时写“无法判断”。
- 失败定位、用例校准或只运行测试只能给本次范围内的局部结论，并明确“不能代表全量验证通过”；只有关键场景和覆盖门禁闭环后才能给完整交付判断。
- “有条件交付”仅用于剩余缺口已证明为低风险且 Owner、补测、监控或回滚条件明确的情况，不能用来弱化关键未测或环境阻塞。

## 主产物

full 写 `06-test-report.md`，quick 写 `03-test-report.md`。它是当前阶段唯一权威主产物，必须记录应测场景、映射、环境与能力、原始执行记录、测试轮次、差异证据链、覆盖缺口和交付结论。详细轮次可写入 `auxiliary/test-rounds/`，但必须由主产物索引且不得覆盖主结论。

主报告必须分别维护“本次范围结论”和“阶段交付判断”；场景记录将“验证结果”与“阻塞原因/解锁条件”分列，避免局部失败定位或环境阻塞被误读为全阶段结论。

交付结论只能是：建议交付、有条件交付、暂缓交付或无法判断，并写清依据、阻塞项和重新判断条件。

## 完成

1. 根据实际结果更新 frontmatter 和开放问题数量；存在 P0、关键失败、关键阻塞或关键未验证时保持 `status: draft`，交付当前结论与重新判断条件，不运行完成命令。
2. 仅当关键场景闭环且无 P0 时才设置 `status: completed`，并运行 `complete-stage --stage test_verify`。
3. CLI 失败时停止推进，报告阶段校验失败、原因和重试动作，不手改 `meta.json`，也不把文档完成声明写成阶段完成。
4. 仅在 CLI 成功后输出阶段交付判断、产物路径、未测项和交付建议。固定流程到此结束，不执行提交、发布或部署。

## 禁止事项

- 不把环境问题改成业务兼容逻辑。
- 不把“测试通过”直接等同于覆盖充分或可以发布。
- 不泄露完整 token、Cookie、Authorization、账号或密码。
- 不把未执行、阻塞或降级验证写成通过。
- 不执行提交、推送、合并或部署。
