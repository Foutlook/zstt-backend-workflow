# ZSTT Artifact Analysis

## 定位

在 Full 任务拆分完成后、编码实现开始前，对 `00-requirement.md`、`01-research.md`、`02-design.md`、`03-tasks.md` 及其索引附件做一次只读横向分析。

本 Skill 补充 Runtime 的确定性结构门禁：Runtime 证明 ID、章节和引用满足契约；本 Skill 进一步检查这些引用表达的业务语义是否一致。它不属于 Full/Quick 固定阶段，不修改 `.zstt/meta.json`，也不替代实现后的 `$zstt-code-review`。

仅当用户明确指定本 Skill 时执行。分析完成后可以建议返回具体上游阶段修正，但不得自动修改产物、调用下游 Skill 或开始编码。

## 开始前

1. 以 UTF-8 读取项目 `AGENTS.md`。
2. 运行 `python .zstt-kit/runtime/rule_resolver.py resolve --skill zstt-artifact-analysis`。
3. 以 UTF-8 完整读取解析结果中每个规则的 `path`，记录 `rulesetVersion`、`rulesetFingerprint`、规则 ID 和选择原因；解析失败或规则缺失时停止，并执行 `zstt check --here`。
4. 确认用户给出的需求目录位于 `.zstt/features/`。用户显式目录优先；未给目录时运行 `current --repo-root <业务仓库>`，只接受当前 Git 分支上的唯一未完成需求。0 个或多个候选时运行 `list --repo-root <业务仓库>` 并要求用户选择，不能按日期猜测。
5. 运行只读命令 `status`，确认模式为 `full`、`task_breakdown` 已完成、`stale_stages` 为空，且 SQL Gate 的有效状态为 `not_involved` 或 `confirmed`。
6. 根据 `status` 锁定实现前窗口：
   - `implementation` 已完成时停止，说明本 Skill 的实现前窗口已经关闭，并推荐用户显式调用 `$zstt-code-review`；
   - `current_stage` 已进入 `implementation` 时，只读检查 `04-implementation.md`。如果其中已有任务执行、代码改动或验证记录，视为实现已经开始并停止；只有文件仍是未执行模板，且用户确认尚未编码时，才继续本次实现前分析；
   - 不得为了继续分析而删除实现记录、回退状态或修改业务代码。
7. 依次对四个阶段运行只读 `validate --stage`。任一产物缺失、失效或结构门禁失败时停止横向分析，指出最早应返回的阶段和解锁动作。
8. 完整读取四份主产物以及其中明确索引的附件。不要读取未被主产物引用的历史草稿来拼接当前结论。

`status` 和 `validate` 只用于读取与校验。禁止调用会创建产物或修改状态的 `prepare-stage`、`complete-stage`、`prepare-sql-gate` 或 `confirm-sql`。

## 建立语义索引

先在内部建立以下索引，不在输出中复述整份原文：

- `Rxx`：需求结论、验收场景、边界和非功能要求；
- `Cxx/Exx/RQxx`：代码事实、证据、限制和待验证问题；
- `Dxx`：已确认设计选择、代码落点、契约、SQL、发布与验证策略；
- `USxx`：只用于任务组织的业务价值切片、来源 `Rxx` 和独立验收信号；
- `Txx`：编码任务、依赖、文件范围、完成标准和验证信号；
- 非编码交接项：SQL 执行、联调、发布、灰度、监控和回滚；
- 统一术语：业务对象、状态、身份字段、接口、表、Topic 和配置名。

只使用显式 ID、章节引用和可核对语义建立映射。关键词相似只能作为复核线索，不能单独证明覆盖关系。

## 分析通道

### 1. 覆盖与范围

- 每个有效 `Rxx` 是否有调研结论、设计承接，以及编码任务或合理的非编码交接；
- 每个 `USxx` 是否来源于有效 `Rxx`、形成真实用户/业务增量并覆盖相应 `Txx`；每个 `Txx` 是否进入某个切片或其前置基础任务；
- 每个核心 `Dxx` 是否被至少一个 `Txx` 或交接项承接；
- 每个 `Txx` 是否有有效 `Dxx` 来源，是否引入上游没有批准的新范围；
- 权限、历史兼容、异常、性能、安全、可观测性、迁移和回滚是否在下游丢失。
- 需求中的量化阈值、观测口径和证据来源是否传递到设计策略、任务完成标准和验证信号。

### 2. 语义一致性

- 同一业务对象、状态、字段和身份维度在四份产物中是否含义一致；
- Guard 条件是否被误写成真实业务依赖；
- 最终数据源、实体集、映射来源和关键参数是否在方案或任务中被替换；
- 已确认的最小方案是否在任务中悄然变成 fallback、新分支或更复杂设计。

### 3. 契约与数据

- HTTP、RPC、MQ、Job、DTO、Jackson 字段及提供方/消费方是否一致；
- SQL、索引、事务、迁移和发布顺序是否与已确认 SQL Gate 范围一致；
- 数据身份、去重、隔离、幂等、并发和历史数据口径是否完整传递；
- 任务预计修改文件是否与真实项目、代码落点和契约归属一致。

### 4. 依赖与执行安全

- 任务依赖是否存在、无环，并与契约、Schema、配置和发布顺序相符；
- 当前可执行集合和禁止提前执行集合是否正确；
- 并行任务是否存在同文件、共享契约、SQL、配置或隐含时序冲突；
- 验证命令、预期信号和失败信号是否足以证明对应任务完成。

### 5. 项目规则对齐

- 需求、方案或任务是否违反 `AGENTS.md` 和已解析的强约束规则；
- 是否出现未解释的复杂度、无证据抽象、N+1、循环远程调用或数据源拆分；
- 规则冲突必须引用具体位置和规则 ID，不能只给通用风格建议。

## 严重级别

- **P0**：会导致需求闭环缺失、业务语义错误、契约/SQL/权限/核心数据身份错误，或违反项目强约束；实现前必须修正。
- **P1**：重要边界、非功能要求、任务依赖或验证策略不完整，继续实现有较高返工风险。
- **P2**：不阻塞核心实现，但会降低可维护性、可读性或交付确定性。

报告严重级别是本次只读分析结论，不得回写 `meta.json` 的阻塞计数。
