# ZSTT Product Feature Analysis

## 定位

回答一个具体的 Java 后端现有功能问题，建立足以让目标读者理解当前行为的最小证据模型。典型问题包括按钮或接口生效条件、状态流转、数据从哪里来、哪些服务参与、某个规则当前是否实现，以及用户明确要求的既有功能变更影响。

本 Skill 是阶段中立的只读辅助能力，不要求先创建 `00-requirement.md`，不推进或修改 `.zstt/meta.json`。它不同于：

- `$zstt-repo-research`：后者服务于已确认需求，形成完整或聚焦的 `01-research.md`；
- `$zstt-bug-fix`：后者确认契约违反、分析问题并在二次确认后修复；
- `$zstt-requirement-clarification`：后者把新需求或变更意图收敛为可实施契约。

## 开始前

1. 运行 `python .zstt-kit/runtime/rule_resolver.py resolve --skill zstt-product-feature-analysis`。
2. 以 UTF-8 完整读取解析结果中每个规则的 `path`，记录 `rulesetVersion`、`rulesetFingerprint`、规则 ID 和选择原因。解析失败或规则缺失时停止，并执行 `zstt check --here`。
3. 完整读取 `references/advanced-playbook.md`，再读取项目 `AGENTS.md` 和用户明确授权的材料。
4. 锁定一个具体问题、目标读者、产品边界和输出深度。只有用户明确要求“影响分析”“如果修改会影响什么”时才分析变更影响。
5. 仅当日志、数据库、部署状态或一次运行事实会改变答案时，锁定唯一的 `test` 或 `prod` 环境；纯静态问题不要求环境。
6. 默认只在当前任务中交付答案。只有用户明确要求保存或生成报告时，才使用 `assets/feature-analysis-template.md` 创建 `.zstt/analyses/features/YYYYMMDD-<feature>.md`；不创建需求目录或阶段产物。

## 问题与证据边界

把以下事实类型分开，避免用一种来源代替另一种：

- **产品意图**：PRD、业务规则或用户确认说明希望怎样工作；
- **当前实现**：适用版本的代码、配置和契约实际实现了什么；
- **运行观察**：一个明确环境、身份和时间窗口内真实发生了什么；
- **持久状态**：数据库、缓存、ES 或消息中的有界状态；
- **分析推断**：由前述事实支持、但未被单一来源直接证明的关系。

PRD 不能证明已经实现，静态代码不能证明某次请求实际执行，一条日志或数据记录也不能代表所有场景。证据冲突时保留冲突及其影响，不选择更顺眼的一方。

## 默认分析路径

1. 用一句话复述目标读者真正需要回答的问题，明确包含范围和不包含范围。范围存在会改变结论的歧义时，只问一个最关键问题。
2. 按 `references/advanced-playbook.md` 确定唯一代码来源。用户给出本地仓库路径时只读取该路径；未给路径时才检查已配置的只读仓库 MCP 或当前已授权仓库上下文，不猜测同名目录。
3. 从用户可观察入口追踪到真实行为点：Controller、Job、Consumer、Service、Facade/Client、Repository/Mapper/SQL，以及确实参与结果的缓存、ES、MQ、配置和横切逻辑。
4. 找到响应字段、状态或副作用的最终查询、计算、赋值、持久化或外部调用点，记录真正影响结果的参数。Guard、判空和字段透传只用于定位，不能自动当作业务依赖。
5. 列表、聚合、图表和映射补全场景，核对最终实体集与 ownership、状态等映射是否来自范围一致的数据源；没有代码、schema、查询或契约证据时，不假设两个来源等价。
6. 只有静态证据无法回答环境特定问题时，才按唯一环境做收敛的 Trace、日志、MySQL 或 ES 只读查询。无命中、超时、未索引和权限不足都是证据缺口，不是“不存在”。
7. 将证据整理为最小功能模型：触发条件、主流程、规则、例外、数据来源、外部副作用和用户结果。只跟随回答问题所需的调用方和下游，不扫描无关仓库。
8. 用户明确要求变更影响时，再从将改变的规则或契约向调用方、消费者、数据、兼容、测试和发布边界扩展；未要求时停在当前行为。

## 输出

先直接回答功能问题，再按实际需要提供：

1. 当前行为、触发条件、规则和例外；
2. 紧凑的用户/API/数据流；
3. 关键代码、配置、运行或数据证据及其事实类型；
4. 证据冲突、未覆盖范围和最小补证动作；
5. 仅在用户明确要求时提供变更影响面。

面向产品或测试时先用业务语言说明，再补必要技术锚点；面向开发时可以提供仓库、版本、文件、符号和关键参数。不要围绕工具调用过程组织答案，也不要输出独立的数值置信度。

## 分流与停止

- 用户要新增或改变行为：停止现状分析，交付已确认基线，并建议显式调用 `$zstt-requirement-clarification`。
- 证据显示可能存在契约违反：说明实际、预期、依据和证据缺口，建议显式调用 `$zstt-bug-fix`；不在本 Skill 中确认缺陷或设计修复。
- 用户只问一个字段、接口或条件：回答到最终数据源或赋值点即可，不升级为完整仓库调研。
- 证据已经足以回答，或所有有界读取都无法解除关键未知时停止；不得为提高表面完整度继续无边界搜索。

## 禁止事项

- 不创建或修改 `00-requirement.md`、`01-research.md`、`02-design.md` 或固定阶段状态。
- 不确认 Bug、分析根因、给出修复方案或修改代码。
- 不把需求目标、测试用例、字段名或相似代码写成当前实现事实。
- 不混用生产和测试环境，不用测试凭据或数据填补生产证据缺口。
- 不自动执行其他 Skill，不自动 commit、push、发布或部署。
