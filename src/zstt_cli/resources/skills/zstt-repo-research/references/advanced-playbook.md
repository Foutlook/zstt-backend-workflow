# 高级仓库调研 Playbook

## 1. 目标

把已澄清需求转换成源码可验证的分析目标，确定仓库边界、主项目、需改仓库、每仓库变更范围、真实调用链、最终数据源、旧链路副作用和运行时缺口。`00-requirement.md` 是需求口径，不是代码事实；任何“应该存在”的能力都必须由源码或运行证据验证。

调研是只读活动，不写技术方案、不修改业务代码，也不因为某个工具方便就无边界扫描当前目录。

## 2. 输入与分析目标

从 `00-requirement.md` 的稳定 `Rxx` 形成验证目标：

```markdown
| 需求 ID | 需求主张 | 代码验证问题 | 验证状态 | 结论 ID | 证据 ID | 风险/RQxx |
|---|---|---|---|---|---|---|
```

完整调研必须且只能覆盖上游全部 `Rxx`，每个 ID 恰好一行；状态使用“已验证”“部分验证”“未覆盖”或“阻塞”。部分验证必须写明证据边界和 `RQxx`，未覆盖或阻塞不能完成阶段。聚焦调研只覆盖声明范围并保持草稿。

目标至少覆盖用户路径、业务规则、数据身份、状态隔离、旧链路禁止项、跨仓库契约和验收能力。需求用语只标为 Requirement claim，不能因为文档写了“新增”就断言代码不存在。需求阶段转交仓库调研的 `Qxx` 也必须在验证矩阵、结论或问题台账中显式承接。

## 3. 仓库边界与主项目

优先从用户、需求主产物、仓库清单、工单信息、模块名、端点名和包名确认仓库边界。明确：

- 主项目：负责用户态或业务态闭环，并承载 `.zstt` 需求目录；
- 依赖仓库：提供契约、数据、计算、配置、消息或共享 SDK；
- 排除仓库：为什么与当前需求无代码变更关系；
- 未知仓库：缺少什么证据才能判断归属。

每个候选仓库只使用以下分类：`Must change`、`May change`、`No code change`、`Runtime/config only`、`Unknown`。仓库出现在调用链中不等于必须修改，必须证明其拥有的接口、行为、schema、配置或数据源需要变化。

如果多个主项目候选同样合理，或远程和本地都无法确认目标仓库，停止并向用户确认，不凭目录名称猜测。

## 4. 工具选择：显式本地路径优先

先做来源选择，再做能力探测。来源优先级是：

```text
用户明确指定仓库路径
  -> 仅使用指定的本地 checkout
未指定仓库路径
  -> 根据明确环境选择 .env.local；未明确时默认 .env.prod.local
  -> with_env.py 注入 repo-mcp Scope
  -> repo_mcp_client.py 探测并使用远程仓库 MCP
以上条件不满足或客户端调用失败
  -> 默认降级
```

来源门禁必须短路（short-circuit）：一旦用户明确指定本地路径，不再读取私有 MCP 配置，也不探测或调用远程仓库能力。

### 4.1 用户指定的本地 checkout

用户在当前请求或权威上游材料中明确给出一个或多个仓库路径时：

1. 解析并验证路径存在，确认它是具体目标 checkout，而不是未确认的多项目父目录；
2. 核对 Git remote、项目清单、模块或需求线索，确认仓库身份；
3. 只在指定路径内读取源码和使用本地工具；
4. 路径无效、仓库身份冲突或缺少依赖仓库时，报告精确缺口并请用户补充，不得自动切换远程 MCP。

工作区中碰巧存在同名目录不等于用户指定路径，也不能据此扩大本地读取范围。

若 CodeGraph 可用：

1. 对每个目标子项目显式检查状态；
2. 检查索引新鲜度和 pending 文件；
3. 用搜索、探索、callers、callees 和 impact 定位关系；
4. 最终结论仍用最新源文件确认。

pending 文件影响主链时，不用旧索引下确定结论；直接读取最新文件，或在得到授权后等待/更新索引。禁止在未确认的父目录初始化或更新索引。

### 4.2 未指定路径时的私有远程 MCP

只有用户没有指定仓库路径时，才使用 Kit 的私有远程仓库配置。用户明确指定测试环境时使用 `.zstt-kit/.env/.env.local`；其他情况默认使用 `.zstt-kit/.env/.env.prod.local`。两份文件都必须受 Git 忽略，并使用相同字段：

```dotenv
ZSTT_REPO_MCP_URL=
```

不要直接读取该值。所有调用必须经过固定客户端：

```text
python .zstt-kit/runtime/with_env.py <test|prod> repo-mcp -- \
  python .zstt-kit/runtime/repo_mcp_client.py probe

python .zstt-kit/runtime/with_env.py <test|prod> repo-mcp -- \
  python .zstt-kit/runtime/repo_mcp_client.py explore \
  --repository <repository> --query <query> --max-files <1-20>
```

规则：

- `with_env.py` 只向仓库客户端注入当前环境的 `ZSTT_REPO_MCP_URL`，不会注入 DMS、Observability 或 ES 凭据；
- `repo_mcp_client.py` 只允许调用 `codegraph_explore`，并负责 MCP 初始化、会话和输出脱敏；
- `probe` 成功只证明端点和工具可用；远程结果仍需证明仓库身份、分支或 ref、索引状态和证据覆盖；
- 禁止使用 Web、curl、PowerShell、普通 HTTP 客户端或当前会话外的临时脚本直接请求私有 URL；
- 不在聊天、命令输出、日志、阶段产物、Skill 或代码中回显真实 URL；
- MCP 返回证据时记录仓库、分支或 ref、文件定位方式、能力覆盖和无法读取范围，不记录私有连接信息。

探测成功后：

1. 根据 Git remote、需求材料或已确认仓库清单确定 `repository`，避免无边界全仓搜索；
2. 确认目标仓库、分支或 ref；
3. 用语义或源码切片定位候选，再读取最终源文件确认；
4. 记录远程能力覆盖和无法读取的范围。

私有配置不存在或不完整、权限不足、仓库不可访问、工具不匹配、客户端调用失败或缺少决定性证据时，转入默认降级。不得把真实 URL、Header、Token 或其他鉴权信息补写到受 Git 管理的文件中。

### 4.3 默认降级

没有显式路径且私有仓库客户端不可用时，沿用当前任务中已经被用户授权并能确认身份的本地仓库上下文；如果无法唯一确认目标仓库，列出所需仓库并向用户索取路径，不按目录名称猜测。

选定可信本地 checkout 后，CodeGraph 不可用、索引不覆盖或远程工具失败时：

- 用 `rg --encoding utf-8` 定位入口、符号、配置和 SQL 候选；
- 读取 Maven/Gradle 清单、模块结构和依赖方向；
- 从入口逐层源码追踪 Service、Facade、Client、Repository、Mapper 和 SQL；
- 用 Git、测试和构建命令补充可复现证据；
- 对反射、AOP、动态路由、配置、MQ、定时任务等无法闭合的关系降低置信度。

`rg` 命中只是候选发现，不等于完整调用链。记录工具失败边界、降级路径、未覆盖范围和证据置信度。

## 5. 固定调研顺序

### 5.1 项目与入口

盘点模块、源码根、测试根、生成代码、构建清单和对外契约。按需求入口检查 Controller、Job、MQ Consumer、Listener、定时任务、工作流节点、RPC/HTTP 服务和公开方法。

每个候选先判断它是否由需求或调用链证明相关；仅仅“看起来类似”的实现不写成结论。

### 5.2 真实调用链

从入口逐层记录：

```text
Entrance -> Service/Manager -> Facade/Client -> Repository/Mapper -> SQL/存储/远程服务
```

同时检查隐式边：依赖注入、AOP、Filter、Interceptor、事件发布订阅、异步线程、事务后动作、重试、补偿、缓存和配置开关。框架连接但运行时选择未证明时标为 Framework inferred。

### 5.3 最终行为与关键参数

追到最终查询、计算、赋值、持久化或远程调用点，记录真正影响结果的参数、实体身份、状态、时间范围、权限、租户和上下文。

Guard 条件只说明是否继续执行。字段只在空判断中出现，不能据此认定它是业务依赖；必须检查最终 fetch、calculation 或 assignment 是否使用该字段。

### 5.4 数据源一致性

聚合、列表、图表和映射补全必须画出：

- 最终实体集来源；
- ownership、章节、状态等映射来源；
- 最终响应字段赋值点；
- 两套来源范围是否由代码、schema、查询或契约证明一致。

没有范围一致证据时，把来源分裂列为首要风险，不用 fallback 或平行查询隐藏。

## 6. 旧链路副作用与反向影响

检查旧状态维度、自动完成、自动推荐、自动同步、排序、候选池、缓存、锁、MQ、ES、定时任务、事务后通知、配置和灰度。

旧能力结论只能是：

- 可直接复用；
- 可扩展复用；
- 只可参考；
- 禁止复用；
- 必须新增。

准备复用或改造旧方法时，必须检查调用方和影响面。反向影响未闭合时不能写“可直接复用”；如果新语义会污染旧场景，降级为禁止复用或必须新增。

## 7. 跨仓库依赖

按仓库分别回答：

- 拥有什么能力和数据；
- API/DTO/RPC/HTTP/MQ 契约是否满足需求；
- 是否需要改服务逻辑、SQL、配置、任务或测试；
- 谁拥有状态，哪些仓库只能查询不能落状态；
- 发布、兼容、迁移和运行时验证依赖；
- 变更分类、证据和置信度。

最终报告必须先给出“需改仓库清单”，再为每个仓库提供匹配的变更范围小节。不能只按需求目标或类名罗列改动。

权威仓库分类和每仓 ChangeScope 使用相同仓库名称。每个候选仓库都必须有范围记录；`No code change` 也写清排除对象和证据，避免只记录需要修改的仓库而遗漏兼容或发布边界。

## 8. 共享语义与当前 SQL 事实

### 8.1 共享状态、枚举和类型码

需求触达共享状态、枚举、类型码、序列化值或历史魔法值时，执行反向影响分析：

```text
生产方 → 数据库/RPC/MQ/JSON/缓存 → 所有消费者 → 历史数据与未知值
```

同时搜索语义对象名称、字段名、序列化值、数字码和历史魔法值，并检查：

- `switch/if`、`IN/NOT IN`、`CASE WHEN`；
- 查询过滤、聚合统计、排序和状态机；
- RPC、JSON、MQ、缓存、ES 和定时任务；
- 旧版本消费者、历史数据和未知枚举值兼容。

`shared_semantic_impact: involved` 时，矩阵必须覆盖生产方、持久化/传播路径和每个已发现消费者，并引用 `Cxx/Exx`。判定为 `none` 时也要记录排除范围和证据，不能用“没搜到”代替完整结论。

### 8.2 当前 SQL 事实

仓库调研只记录当前 SQL 事实和变化触发点：

- SQL/XML/注解或构造器位置；
- SELECT、INSERT、UPDATE、DELETE 或 DDL 类型；
- 当前 JOIN、过滤、排序、分页和写入条件；
- 乐观锁、幂等、租户、状态或时间条件；
- 为什么当前需求可能改变这些语义。

使用 `SQLxx` 标识事实记录并关联 `Cxx/Exx`。`current_sql_impact: involved` 时至少有一条完整事实；`none` 时提供排除依据。未来 SQL、迁移脚本、用户确认和语义指纹仍由技术设计阶段负责，避免把方案混入代码事实。

## 9. Claim Ledger、证据与问题台账

每个影响技术方案、接口、SQL、任务或复用判断的结论都进入 Claim Ledger：

```markdown
| 结论 ID | 结论 | 证据 ID | 等级 | 代码位置 | 反证 | 覆盖度 | 置信度 | 运行时缺口 | 待验证动作 |
|---|---|---|---|---|---|---|---|---|---|
```

规则：

- 每个 `Cxx` 至少引用一个可反查的 `Exx`；
- `Cxx/Exx` 分别唯一，引用不存在或重复的 ID 视为未闭环；
- 证据等级只能是 Proven、Framework inferred、Requirement claim、Runtime dependent 或 Unknown；
- 本地文件证据写仓库和真实 `path:line` 或符号，可解析时必须验证文件和行号存在；
- 远程源码、配置、日志、Trace、消息、数据库和用户口径证据写明定位方式与限制；
- 高置信结论必须有闭合源码或运行证据；
- “未找到”只能写“当前证据范围内未发现”，并说明搜索范围；
- 关键词、类名、相似实现和需求声明不能单独支撑确定结论；
- 记录反证和冲突来源，避免只收集支持当前猜测的材料；
- 覆盖度标明已覆盖代码、未覆盖范围、工具路径和运行时验证缺口。

运行时缺口按配置、接口、日志/Trace、消息/任务、测试数据或用户口径分类，并给出具体验证动作。

调研问题使用 `RQxx`，避免与需求澄清的 `Qxx` 混淆。问题类型、承接边界如下：

| 类型 | Owner/承接阶段 | 规则 |
|---|---|---|
| 用户意图 | 用户/需求澄清 | 不用代码事实替用户决定产品语义 |
| 代码事实 | 仓库调研 | 继续取证或说明当前覆盖边界 |
| 运行时证据 | 测试环境/运维/用户 | 给出具体日志、配置、数据或请求验证动作 |
| 设计选择 | 技术设计 | 业务事实已明确后再比较方案 |

问题状态使用“待处理”“已解决”或“转下游”。P0 待处理问题阻塞完成；转下游必须写明影响和解锁动作，不能只靠改状态清零。

## 10. 用户纠正与上游回写

用户纠正或调研发现需求口径错误时：

- 影响范围、路径、业务规则、身份、状态、权限、旧链路禁止项或验收的，回写 `00-requirement.md`；
- 只影响代码事实、仓库边界、复用性和实现落点的，更新 `01-research.md`。

回写后重新校验受影响目标和结论账本，删除被推翻旧口径。不要让两份主产物保留互相矛盾的当前结论。

## 11. 完成检查

- 需求验证矩阵完整且只能覆盖上游全部 `Rxx`，没有重复、未知、未覆盖或阻塞项；
- 仓库边界、主项目、依赖仓库和排除项清晰；
- 权威仓库分类与每仓 ChangeScope 一一对应；
- 仓库来源优先级、私有 MCP 探测结果、本地 checkout、CodeGraph、索引新鲜度和默认降级均有记录，且不包含私有配置值；
- 主链、最终数据源、关键参数和 Guard/真实依赖已闭环；
- 旧链路副作用、反向影响和跨仓库契约已检查；
- 共享语义和当前 SQL 影响已判定；涉及时矩阵完整，不涉及时有排除证据；
- 每个重要结论都有 Claim Ledger、反证、证据覆盖度和待验证动作；
- `Cxx/Exx/RQxx` 唯一且引用闭环，本地可解析证据的文件和行号有效；
- 运行时验证缺口不会被静态推断冒充；
- 没有影响方案的 P0，才能完成阶段并推荐技术方案。
