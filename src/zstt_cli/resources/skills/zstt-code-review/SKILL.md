# ZSTT Code Review

## 定位

这是实现后的独立证据化评审。默认只读，不直接修改代码；用户要求修复时，也先完成评审产物，再推荐重新调用实现阶段。

仅当用户明确指定本 Skill 时执行。Review 通过后可以推荐 `$zstt-test-verify`，但不得自动执行推荐的下一阶段。

## 开始前

1. 运行 `python .zstt-kit/runtime/rule_resolver.py resolve --skill zstt-code-review`。
2. 以 UTF-8 完整读取解析结果中每个规则的 `path`，记录 `rulesetVersion`、`rulesetFingerprint`、规则 ID 和选择原因。解析失败或规则缺失时停止，并执行 `zstt check --here`。
3. 完整读取本阶段 `references/advanced-playbook.md`。
4. 读取当前 Git diff、完整被改文件、相关调用方、测试和实现记录。根据真实风险面追加 `jackson`、`data-access`、`transaction`、`concurrency`、`abstraction`、`design-patterns` 或 `ddd` 等上下文并重新解析；不要只看局部 diff，也不要为填清单加载无关规则。
5. 运行 `python .zstt-kit/runtime/workflow_cli.py prepare-stage --stage code_review --feature-dir <需求目录>`，重新校验上游。

## 评审强度

1. 接口/SQL/配置/消息、跨仓库、核心状态、权限、事务并发、安全或多任务 diff 执行完整评审，覆盖全部一致性矩阵、执行链、专项风险和幻觉审计。
2. 单个 DTO、方法或小范围行为修复且验证证据完整时执行聚焦评审，只展开本次改动实际触达的需求、契约和风险面。
3. 聚焦评审仍读取完整被改文件、必要调用方和测试，执行幻觉审计；DTO 至少核对 JSON/Jackson 命名、序列化反序列化、兼容和调用端契约。
4. 与当前风险面无关的 SQL、MQ、事务等清单项标记“不适用”后停止，不为填满矩阵扩读或制造建议。
5. 聚焦过程中发现契约、数据范围、权限、状态、事务、跨仓调用或证据断裂时，只扩展受影响风险面并说明原因；无法可靠评审时转为阻塞，不给通过结论。

## 评审顺序

1. 固定评审范围：基线、工作区状态、diff、修改文件和未跟踪业务文件。
2. 建立需求、方案、任务与实现一致性矩阵，检查遗漏和越界修改。
3. 反向追踪真实入口、调用链、最终数据源、最终赋值/计算点和关键参数。
4. 区分 Guard 条件与真实业务依赖，检查数据源范围是否闭环。
5. 检查接口、DTO/Jackson、SQL、事务、状态、权限、异常、兼容、并发和安全。
6. 检查 N+1、循环远程调用、批量性能、无效抽象和过度设计。
7. 检查注释保留、关键原因注释、日志/Trace 和验证证据是否真实。
8. 执行幻觉审计；范围足够大且工具可用时可进行只读专项并行审查，但所有候选问题必须由主上下文复核。

## 问题输出

问题按 P0/P1/P2/P3 排序：

- P0：会造成严重数据、安全、不可逆发布或核心链路故障；
- P1：明确的功能错误、需求偏差或高概率回归；
- P2：边界、性能、可维护性或测试缺口；
- P3：低风险但值得修正的问题。

每条问题必须包含代码位置、失败条件、影响、证据链和最小修复方向。没有任何需要修改的问题时才写“未发现需要修改的问题”；仅 P0 为零但仍有 P1/P2/P3 时必须完整列出，不能写成无问题。不要为了显得严格而制造建议。

## 主产物

full 写 `05-code-review.md`，quick 写 `02-code-review.md`。报告包含评审输入、一致性矩阵、真实执行链、幻觉审计、问题清单、Java 质量检查、验证复核和结论；详细 Review 轮次可写入 `auxiliary/review-rounds/`，主产物保持当前权威结论。

- 产物文件名只由 `meta.json` 的 full/quick 模式决定；评审强度由本次变更风险决定，两者不得互相推断。
- 完整评审填写全部一致性、执行链、专项风险、幻觉和验证章节。
- 聚焦评审保留固定章节，只展开受影响需求/契约、最短真实执行链、相关 Java 风险、幻觉审计和验证证据；无关风险面写明“不适用及原因”后停止。
- 聚焦结论至少包含冻结范围、核验过的契约或行为、证据命令与结果、问题或明确无问题、未覆盖边界，不用空表撑满报告。
- 修复复审仍写回同一主产物；辅助轮次只保存历史证据，不产生第二份当前结论。

## 完成

1. 重算 P0/P1/P2/P3；有 P0 时保持 `status: draft`，交付阻塞问题和解锁动作，不运行完成命令。
2. 仅当 P0 为零且评审结论可交付时才设置 `status: completed`，并运行 `complete-stage --stage code_review`。
3. CLI 失败时停止推进，报告失败原因和重试动作，不手改 `meta.json`，也不推荐执行下游阶段。
4. 仅在 CLI 成功后分流：存在未关闭 P1/P2/P3 时推荐 `$zstt-implementation`；确认没有需要修改的问题时推荐 `$zstt-test-verify`。两者都不自动执行。

## 禁止事项

- 不自动修复代码，不自动执行推荐步骤。
- 不把风格偏好当作功能缺陷。
- 不只凭测试为绿就判断实现正确。
