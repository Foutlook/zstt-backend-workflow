# 高级代码评审 Playbook

## 1. 目标和顺序

判断本次实现是否符合用户最新需求、ZSTT 主产物、真实代码和可复现验证，并能否安全进入测试。固定顺序：可评审性、需求/方案/任务一致性、diff 反查、真实调用链、并行合并检查、幻觉审计、代码质量和验证证据。

默认只读。用户要求修复时，仍先完成当前 Review 轮次和修复范围，再推荐显式调用 `$zstt-implementation`；修复完成后开启新的修复复审，旧通过结论不自动有效。

## 2. 范围冻结与可评审性

先记录：

- `git status --short`；
- 未暂存和已暂存 diff；
- 未跟踪业务文件的完整内容；
- 用户指定文件、任务、提交或需求目录；
- 当前基线提交、实现记录和已有 Review 轮次；
- 被改文件的完整上下文、直接调用方和测试。

范围冻结表：

```markdown
| 文件 | 变更类型 | 来源任务/执行者 | 需求/设计/接口/SQL 映射 | 风险面 | 验证证据 |
|---|---|---|---|---|---|
```

变更类型使用业务代码、接口契约、SQL/Mapper、配置、依赖、测试、文档或生成文件。

先做可评审性门禁：无关需求、格式化、批量 import、生成文件或历史清理不能混入；高风险 diff 无任务映射或过大到无法可靠理解时，不给通过结论，要求按任务或风险面拆分。

## 3. 权威顺序与一致性矩阵

full 以用户最新确认、`00-requirement.md`、`01-research.md`、`02-design.md`、`03-tasks.md`、实现记录和辅助附件为输入。quick 以用户最新确认、`00-requirement.md`、quick 实现记录、diff 和代码事实为输入。

建立一致性矩阵：

```markdown
| 检查项 | 需求 | Cxx/Dxx/任务 | 实现位置 | 验证证据 | 结论 | 回写位置 |
|---|---|---|---|---|---|---|
```

逐项检查：

- 需求目标、用户路径、规则、身份、状态、权限、验收和非目标；
- 调研确认的入口、数据源、复用边界和旧链路风险；
- 方案中的接口、SQL、缓存、消息、事务、兼容、发布和回滚；
- 任务覆盖、文件范围、并行写集和完成标准；
- 实现记录、实际 diff 和测试证据。

文档承诺但代码没有落点是遗漏；代码增加文档未记录的接口、字段、SQL、配置、消息或旧链路是越界。类名和局部分层不同但行为一致、且更符合当前代码时，不把个人偏好列为问题，但应记录需要回写的文档。

## 4. 真实执行链复核

从修改入口反向和正向检查完整链路：Controller/Job/Consumer、Service/Manager、Facade/Client、Repository/Mapper/SQL、缓存、消息和外部服务。追到最终查询、计算、赋值、持久化或远程调用点。

检查真正影响结果的参数、实体身份、状态、权限、租户和时间范围。Guard 非空判断不是业务依赖证据；聚合实体集和响应映射来自不同来源时，必须证明范围一致。

## 5. 并行实现审查

仅在实现使用 Codex 子任务时执行。不能只相信子任务自报，要从任务表、实现记录和 git diff 反查：

- 文件锁和实际修改是否一致；
- 是否改了禁止文件、只读参考或未分配文件；
- 是否两个执行者修改同一 Java、Mapper XML、SQL、配置或契约；
- Provider/Consumer、消息两端和 SQL 字段是否先锁定；
- 合并顺序是否符合依赖；
- 主上下文是否完成位置复核、完整 diff 审查和集成验证；
- 并行发现的设计偏差是否已上游回写。

越界写、同文件多执行者或未锁契约两端同时改属于 P0/P1，按真实影响定级。

## 6. 幻觉审计

幻觉审计是固定门禁，不因测试为绿而跳过：

1. **无证据结论**：调研、方案、任务、实现或交付中的关键判断是否缺少 `Cxx/Exx`、代码位置、命令或运行证据；
2. **文档有、代码无**：需求、设计、接口、SQL 或任务承诺是否没有实现；
3. **代码有、文档无**：diff 是否出现范围外能力或未回写偏差；
4. **测试声称通过但无证据**：是否缺少命令、退出码、请求响应、日志或数据回查；
5. **未覆盖写成不存在**：CodeGraph/`rg` 未命中、配置未查或环境未验证是否被写成“没有”；
6. **证据等级越权**：推断、Unknown 或 Runtime dependent 是否被当成 Proven；
7. **过时证据**：用户修改上游、代码或配置后，旧结论是否仍被复用。

审计表：

```markdown
| 审计项 | 结论 | 证据 | 反证/缺口 | 风险 | 处理建议 |
|---|---|---|---|---|---|
```

影响业务口径、接口、SQL、权限、状态、数据一致性或旧链路副作用的无证据结论不得通过。

## 7. 可选专项并行审查

环境支持并且评审范围足够大时，可在当前 Review 阶段内进行只读专项并行审查：

- 业务正确性与需求一致性；
- 数据、SQL、事务和并发；
- 接口、Jackson 和兼容；
- 性能、N+1 和资源；
- 安全、权限和敏感数据；
- 测试、发布和可观测性。

工具不可用或范围较小时串行执行同一清单。专项结果只是候选问题，主上下文必须完成问题去重、位置复核、失败条件验证、影响判断和证据补齐后才能写入报告。专项审查不得修改代码、推进阶段或自动调用实现。

## 8. Java 质量补查

一致性和幻觉审计后检查：

- 功能正确性、空值、状态、异常和主链可读性；
- 无效抽象、过度设计、万能类和无业务语义的 Helper；
- DTO 类型、JSON 字段、`@JsonProperty`、权限身份和兼容；
- SQL 显式字段、N+1、批量、逻辑删除、租户权限、分页排序和索引；
- 事务、DB/缓存/MQ 顺序、幂等、重试、补偿和一致性；
- 循环远程调用、大集合、日志、内存和资源；
- 越权、注入、敏感数据和不可信输入；
- 注释保留、业务原因注释、日志/Trace、异常堆栈；
- 依赖、配置、灰度、定时任务和回滚；
- 编译、单测、接口和回归证据。

只记录本次改动引入或暴露且会影响交付的问题，不把无关历史坏味道列为必须修。

## 9. 问题格式与严重度

每条问题必须有 P0/P1/P2/P3、文件和行号或全局依据、失败条件、影响、证据链和最小修复方向。

- P0：严重数据、安全、不可逆发布或核心链路故障；
- P1：明确功能错误、契约/需求偏差或高概率回归；
- P2：重要边界、性能、维护性或测试缺口；
- P3：低风险且有明确价值的改善。

没有可操作问题时写“未发现需要修改的问题”，并说明未覆盖验证。不要为了显得严格制造风格建议。

## 10. Review 轮次与修复复审

`05-code-review.md` 或 quick 主产物始终保存当前权威结论。详细 Review 轮次可以写入 `auxiliary/review-rounds/review-rNN.md`：

- 新评审递增 R1/R2，不覆盖历史；
- 主产物索引每轮范围、结论和未关闭问题；
- 修复复审读取上一轮问题，标记 fixed、accepted、not-applicable 或 open；
- 重新读取新 diff，不沿用旧位置和旧通过结论；
- 修复扩大到接口、SQL、配置、事务或核心链时，重新做完整一致性和幻觉审计。

附件不能推进阶段；当前主产物完成后才运行 `complete-stage --stage code_review`。

## 11. 结论

结论写“通过”“需修改后通过”或“阻塞”，并分别说明可评审性、需求一致性、方案/任务一致性、并行合并、幻觉审计、代码质量、注释日志和测试缺口。

有问题时推荐 `$zstt-implementation`；通过时推荐 `$zstt-test-verify`。两者都不得自动执行。
