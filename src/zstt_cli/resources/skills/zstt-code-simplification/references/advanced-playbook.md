# 代码简化高级执行手册

本手册用于 cleanup-only 的行为保持型重构。用户明确调用本 Skill 后，默认直接应用安全清理；用户说“只看”“只评审”“不要修改”时切换为报告模式。

## 1. 范围优先级

按以下范围优先级选择并在开始时明确说明：

1. 用户指定的文件、目录、类、方法或符号；
2. 用户指定的提交、提交数量、分支、PR 或日期范围；
3. 未暂存 diff、暂存 diff 和相关未跟踪业务文件；
4. 工作区干净且用户未指定范围时，最近一次提交。

指定符号时定位定义并读取完整文件，再按需读取直接调用方、测试和候选复用实现，不能只看搜索片段。忽略范围外历史代码和无关未跟踪文件。开始后固定范围；证明复用等价性所需的最小相邻上下文可以读取，但不能借机重构整个模块。

## 2. 四个独立视角

### Code Reuse

检查当前范围是否重复了已有 helper、mapper/repository/service 方法、转换器、枚举、校验或格式化逻辑。只有接口语义、数据范围、异常、权限、边界和调用时机均等价时才复用；名字相似不构成证据。

### Simplification

检查冗余状态、中间变量、重复分支、深层嵌套、copy-paste、死代码、无用兼容层和难读控制流。清晰优先于更少行数，拒绝难读的一行式表达、嵌套三元和单次使用的过度抽象。

### Efficiency

检查明确的重复计算、对象构造、序列化、循环内 DB/RPC/API 调用、可复用结果重复获取、无意义集合转换或阻塞初始化。不能把循环单查换成另一种 N+1；涉及数据范围、并发、缓存一致性和时序的优化仅在证据充分时应用。

### Abstraction Level

检查职责和抽象层级：业务规则是否泄漏到 Controller，通用校验是否散落，底层工具是否反向依赖上层对象，局部 fallback 是否掩盖数据源或机制问题。优先最小闭环，不创建万能帮助类或单次使用层。

## 3. 强制并发分析

显式调用本 Skill 即授权使用只读子 Agent。主 Agent 完成范围冻结和最小上下文读取后，必须连续发起至少两个子 Agent `spawn` 请求；全部请求被调度器接受前，不得对任何子 Agent 执行 `wait` 或 `read`。`queued` 或 `running` 均视为成功启动，这样可以避免表面上使用多个 Agent、实际上串行执行。

优先使用四个独立角色：

| 子 Agent | 负责视角 | 必须返回 |
|---|---|---|
| Reuse | Code Reuse | 重复能力、可复用实现、语义等价或不等价证据 |
| Simplification | Simplification | 冗余状态、分支、嵌套、临时变量和最小简化建议 |
| Efficiency | Efficiency | 重复计算、N+1、循环远程调用和集合转换证据 |
| Abstraction | Abstraction Level | 抽象层错位、单次使用层、fallback 和设计模式适用性 |

不含主 Agent、可同时调度的子 Agent 槽位少于四个时按固定规则合并，保证职责清楚且四视角无遗漏：

| 可用子 Agent 数 | 分工 |
|---|---|
| 3 | Reuse；Simplification；Efficiency + Abstraction Level |
| 2 | Code Reuse + Abstraction Level；Simplification + Efficiency |
| 0–1 | 不满足并发协议，禁止自动修改，改为只读阻塞报告 |

每个子 Agent 读取同一冻结范围，并按固定结构返回：

```text
status: completed | blocked | failed
covered_views: [实际完成的视角]
candidates: [候选列表，可以为空]
blocked_reason: null | 具体原因
```

每个候选包含候选 ID、位置、视角、代码证据、行为风险、最小建议和建议优先级，不直接写文件。`status=completed` 且 `candidates=[]` 表示该视角已完成检查但没有候选，属于有效结果。主 Agent 在子 Agent 运行期间核验真实调用链、最终数据源、关键参数和验证基线；收到结果后完成去重、位置复核、行为等价核验和最终分级，再统一应用，避免重复修改或冲突。

子 Agent 工具不可用、并发容量不足两个、启动失败、任务未完成检查、未覆盖约定视角或未返回约定字段时，不得声称已完成并发检查。最终汇总必须说明实际启动数、完成数、缺失视角、未自动修改原因和具备什么条件后可以重新执行。

## 4. 候选项去重与统一应用

将四路发现合并为候选清单：

| 候选 | 位置 | 视角 | 等价证据 | 风险 | 决策 | 未自动修改原因 |
|---|---|---|---|---|---|---|

候选项去重后按规则处理：

| 结论 | 处理 |
|---|---|
| 行为不变、证据充分、范围可控且可验证 | 统一应用 |
| 已确认的正确性、安全、数据、兼容或核心链路高风险 | 记为 P0 推荐；不自动修改行为 |
| 收益明确，但无法证明契约、数据范围、事务、并发或模块边界保持不变，缺少关键验证，或有具体证据但疑似 Bug/安全问题尚待专项诊断 | 记为 P1 推荐；写明未自动修改原因 |
| 方向明确的非阻塞维护性清理，但超出范围、当前验证不足，或因报告模式被用户限制为只读 | 记为 P2 推荐；写明重新处理条件或“报告模式（用户明确限制只读）” |
| 误报、纯风格偏好或证据不足到无法形成修改方向 | 驳回，不包装成推荐项 |

跨文件或修改量大本身不构成 P1，也不自动等于高风险。收益明确、行为等价且验证闭环时，应进入高收益大范围自主修改路径。不能用猜测性 fallback 补齐未知语义。

## 5. 高收益大范围自主修改

应用模式下，不得仅因改动文件多、行数多或需要小型共享抽取而请求额外批准。先建立可审计的收益与成本证据：

“自主实施”只免除因规模产生的重复请示，不覆盖用户当前的只读或范围限制、仓库级 `AGENTS.md`/项目规范门禁、外部系统审批和破坏性操作审批。更高优先级约束要求计划、确认或停止时，必须先遵守并在最终汇总中说明。

| 维度 | 需要记录的证据 |
|---|---|
| 收益 | 等价重复点数量、可减少的 DB/RPC/API 调用或重复计算、可消除的重复分支、后续同步维护点 |
| 修改成本 | 涉及文件和预估行数、候选组数量、是否新增小型共享能力 |
| 回归成本 | 可用测试、编译和静态检查，关键行为覆盖范围，无法覆盖的缺口 |
| 等价边界 | 接口、数据范围、异常、权限、调用顺序、事务、并发、时序和副作用 |

### 5.1 硬门禁

收益评分之前先检查行为、范围、抽象、验证和更高优先级约束。任一门禁失败时直接转为推荐项；收益再高也不能抵消：

| 门禁 | 通过条件 |
|---|---|
| 行为 | 接口、数据、异常、权限、顺序、事务、并发、时序和副作用均有等价证据 |
| 范围 | 写集闭合，范围外文件已重新冻结，无用户改动覆盖 |
| 抽象 | 归属自然、至少 3 个真实使用点，不改变模块或生命周期边界 |
| 验证 | 修改前基线可执行，聚焦测试和完整相关测试能够覆盖关键行为 |
| 约束 | 用户限制、`AGENTS.md`、项目规范及必要审批均已满足 |

### 5.2 收益、成本和置信度评分

使用以下公式：

```text
调整后 ROI = B / max(C, 1) * E
```

收益分 `B` 为 0–10：

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
|---|---|---|---|---|
| 等价重复与复用 | 无重复证据 | 2 处 | 3–4 处 | 不少于 5 处 |
| 运行时收益 | 无证据 | 减少本地转换或计算 | 减少已证只读的重复 DB/RPC/API | 有指标的热点或批量收益 |
| 维护点减少 | 无 | 减少单文件分支或同步点 | 减少跨文件同步维护点 | 不适用，最高 2 分 |
| 稳定能力复用 | 新能力且未验证 | 新增边界稳定的小型共享能力 | 复用已有稳定能力 | 不适用，最高 2 分 |

修改成本分 `C` 为 0–10：

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
|---|---|---|---|---|
| 写集规模 | 1–2 个文件 | 3–5 个文件 | 不少于 6 个文件 | 不适用，最高 2 分 |
| 边界复杂度 | 局部实现 | 同模块共享边界 | 跨模块私有协作 | 公共契约、事务或并发边界 |
| 新增抽象 | 不新增 | 小型共享能力 | 新层或多处依赖调整 | 不适用，最高 2 分 |
| 验证与恢复 | 聚焦和完整测试齐全 | 覆盖充分但执行成本较高 | 存在非关键缺口 | 关键验证或恢复困难 |

证据置信度 `E`：

| 证据等级 | E |
|---|---:|
| 只有静态代码证据 | 0.5 |
| 代码证据 + 聚焦测试 | 0.75 |
| 再有模块测试或完整相关测试 | 0.9 |
| 再有运行指标或基准 | 1.0 |

每项分数必须记录具体文件、行号、调用链、测试命令或指标。相同证据不能在多个维度重复计分；“看起来更简单”“预计收益很高”不能得分。按可独立实施和验证的候选组或批次分别评分，高收益批次不能补贴其他未达阈值的批次。

### 5.3 多 Agent 一致性

四视角候选合并并划分候选组后，至少两个只读子 Agent 对每个候选组及其证据并发独立评分，互不查看对方结论。每份评分返回：

```text
hard_gates: 各门禁 pass | fail 及证据
benefit_score: B
cost_score: C
evidence_confidence: E
adjusted_roi: B / max(C, 1) * E
score_evidence: 每个分项的证据位置
```

若硬门禁结论不同、B 或 C 的最大差值超过 1 分、E 的最大差值超过 0.1，不得用平均分掩盖分歧。主 Agent 回到真实代码、调用链和测试消除分歧后重新评分。结论一致时使用保守值：`B = min(Bi)`、`C = max(Ci)`、`E = min(Ei)`。

每个自主修改批次必须同时满足：全部硬门禁通过、`B >= 7`、`E >= 0.9`、调整后 ROI 不低于 1.5、至少两个子 Agent 评分一致。阈值使用未四舍五入的原始结果，不能把低于 1.5 的 ROI 进位后放行。任一条件不满足时只把该批次转为 P1/P2 推荐，不影响其他独立且通过门禁的批次。

以下情况可判定为高收益：

- 通常不少于 3 个使用点存在已证明等价的重复实现，可以一次消除重复及后续同步维护；
- 批量或热点链路能明确减少重复查询、远程调用、序列化、计算或集合转换；其中 DB/RPC/API 调用必须证明只读或无副作用，并且不改变结果集、顺序、缓存一致性、取数时机、事务和时序；
- 已有稳定公共能力与当前实现语义完全等价，可替换多处本地重复实现；
- 收益可以由静态计数、调用次数变化或测试/基准信号验证，而修改和回归成本处于已覆盖、可分批的闭环内。

单纯减少代码行数、统一个人风格或为未来可能预留抽象不算高收益。新建共享能力时，要求通常不少于 3 个真实等价使用点、归属自然且边界稳定；若会改变模块职责、公共契约、依赖注入、生命周期、事务或并发边界，转为 P1 或模块重构，不在本 Skill 自主实施。

通过收益、行为、范围、抽象和验证门禁后，主 Agent 可以自主实施，不因规模再次请求批准。执行步骤：

1. 按独立候选组建立批次和写集，标明每批收益、行为等价证据、涉及文件和验证命令。若需要写入原冻结范围外的最小闭环文件，先列明新增文件及原因并重新冻结范围。
2. 记录修改前基线；基线不可执行或关键行为无验证覆盖时，不进入自主修改。
3. 一次只应用一个批次，立即运行该批聚焦验证；通过后再继续下一批。
4. 全部批次完成后运行完整相关验证，并复核最终 diff、注释、编码，以及与候选无关的用户改动是否完整保留。
5. 任一批验证失败、等价证据被推翻、写集冲突或收益明显低于预期时，停止后续批次；只修复或还原当前批次由本 Skill 产生的改动，不使用破坏性 Git 命令，剩余项转为 P1/P2 推荐。
6. 各批聚焦验证都通过但最终完整相关验证失败时，不得声明完成；定位跨批次交互，修复或还原本 Skill 涉及的冲突批次，重新通过完整验证后才能交付成功。

## 6. Java 后端边界

- 保持接口契约、业务语义、返回结构、数据范围、异常行为、调用顺序、事务和并发行为不变；
- 聚合、统计、图和映射逻辑不得混用未经证明同范围的数据源；
- 批量场景先收集参数再批量读取，不在循环中逐条访问数据库、RPC 或外部 API；
- `zValue`、`pType`、`uId` 等 JavaBean/Jackson 高风险字段只在本次范围确实涉及绑定时核验 `@JsonProperty`，不能借 cleanup 改接口字段名；
- 简单 getter、常量和一层调用可保持 inline，只为复杂表达式、复用值或调试价值提取局部变量；
- 不删除、改写或清理范围外注释，移动代码时同步保留相关注释。

## 7. 修改前后验证

修改前后使用同一组验证命令和同一判定口径：先记录最接近范围的测试、编译、静态检查命令及结果，修改后再重新执行，证明行为不变；只有新增的必要聚焦检查可以追加，不能偷换验证基线。

高收益大范围修改必须逐批运行聚焦验证，并在全部批次完成后运行完整相关验证。检查最终 diff，确认每一处修改都来自已核验候选项，没有意外注释丢失、范围扩张或用户改动覆盖。Maven 项目若 smart-doc 绑定早期生命周期，而目标只是业务代码验证，可按项目约束使用 `-Dsmart-doc.phase=verify`。

验证无法运行时说明原因、未证明边界和剩余风险；不得把“静态看起来没问题”写成验证通过，也不得用破坏性 Git 命令丢弃用户改动。

## 8. 流程中立与输出

本 Skill 可在任何时刻独立执行，不修改 `.zstt/meta.json`，不推进或回退任何阶段。关联某个 ZSTT 特性时，可把摘要写入 `<feature-dir>/auxiliary/code-simplification-YYYYMMDD-HHmm.md`；该文件不是阶段主产物。

最终输出必须形成一份可快速决策的汇总：

1. **执行概览**：模式、范围、最小上下文、子 Agent 启动/完成数、分工、四视角覆盖和验证基线；高收益大范围修改还要给出规模预估、收益证据、硬门禁结论、两个子 Agent 的独立评分、保守聚合后的 B/C/E、调整后 ROI 和批次划分。
2. **已修改**：每项以 `A-xx` 编号，分别列出位置、改了什么、为什么改、收益与评分证据、调整后 ROI、行为保持依据、所属批次和验证结果；无修改时写明总体原因。
3. **推荐修改（未自动修改）**：按 P0、P1、P2 分节，每项以 `R-xx` 编号，分别列出位置、推荐怎么改、推荐原因、未自动修改原因、证据或影响和下一步；空级别明确写“无”。
4. **验证与边界**：修改前后同口径验证、逐批结果、最终完整相关验证、实际收益、最终 diff、注释与 UTF-8 无 BOM 检查；未执行项说明原因。

推荐项的“未自动修改原因”必须落到报告模式（用户明确限制只读）、可能改变行为、证据不足、评分不一致或未达到自主修改阈值、收益不足以覆盖修改与回归成本、超出冻结范围、缺少验证条件、疑似 Bug/安全问题、与用户改动冲突或并发能力不足等具体类别。不要把已修改内容、推荐项和被驳回候选混写，也不能只给一句“风险较高”。

没有可自动修改项时，“已修改”写“无”，但仍输出有效推荐；只有既无自动修改项、也无有效推荐项时才写真正空结果。不得自动触发固定流程，也不得自动 commit、push、合并或部署。
