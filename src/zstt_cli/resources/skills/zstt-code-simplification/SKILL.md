# ZSTT Code Simplification

## 定位

对用户指定范围做行为保持型简化。它不属于固定流程，不推进、不回退也不修改 `.zstt/meta.json`，可在实现中、Review 后或独立维护时使用。

仅当用户明确指定本 Skill 时执行。

开始前运行 `python .zstt-kit/runtime/rule_resolver.py resolve --skill zstt-code-simplification`，以 UTF-8 完整读取返回的规则 `path`，并记录规则集版本、指纹、规则 ID 和原因；解析失败或规则缺失时停止并执行 `zstt check --here`。随后读取 `references/advanced-playbook.md`。冻结范围并读取完整文件后，只按真实行为面追加 `data-access`、`concurrency`、`abstraction` 或 `design-patterns` 等上下文并重新解析，不能只凭文件名或关键词选规则。

## 范围选择

优先级：

1. 用户指定的文件或符号；
2. 用户指定提交或提交范围；
3. 当前 diff（未暂存和已暂存）；
4. 工作区干净且用户未指定范围时，使用最新提交。

指定符号时读取完整文件和相关调用方，不只看搜索片段。开始前固定范围，避免清理扩散。

## 模式与检查强度

1. 用户要求“只看”“只评审”或“不要修改”时进入报告模式；只交付候选、等价证据、跳过原因和验证建议，不写文件，也不重复执行修改前后验证。
2. 其他明确简化请求进入应用模式；修改前记录验证基线，只直接应用通过行为等价核验的安全候选。
3. 单个符号或单文件属于窄范围：仍须并发启动至少两个只读子 Agent，但可以合并视角分工；不输出重复报告，也不为填矩阵扩读无关上下文。
4. 提交、diff 或多文件范围优先为四个视角各分配一个只读子 Agent；并发容量有限时按本 Skill 的合并规则分工，主 Agent 汇总完整候选清单后统一应用或报告。
5. 无论范围大小，四视角都必须覆盖；检查强度只决定组织方式和证据深度，不降低接口、异常、数据范围、事务或并发门禁。
6. 应用模式中，改动文件数或行数较大不构成转为报告模式或请求额外批准的理由；满足“高收益大范围自主修改”全部门禁时，由主 Agent 自主分批实施。

## 停止与冲突边界

- 用户明确指定的文件或符号无法定位、读取时，报告已探测位置、能力限制和所需最小路径或权限后停止；不得静默改用当前 diff 或最新提交。
- 冻结范围不包含用户请求检查的代码时，以空结果收口，不扩展到范围外寻找可改内容。
- 四视角检查后没有可自动修改项时，只在“已修改”中写“无”，仍须输出全部有效推荐；只有既无自动修改项、也无有效推荐项时才算真正空结果。
- 请求同时包含“只评审”和“直接修改”等冲突授权时，先按报告模式完成只读检查并请求用户确认；获得明确修改授权前不写文件。
- 若在四视角检查前因目标不可用或空范围停止，输出中将各视角标为“未执行/不适用”并说明原因，不得声称已经覆盖。

## 检查角度

- 复用：是否重复已有工具、查询、转换或公共能力；
- 简化：是否存在不必要分支、嵌套、临时变量或重复判断；
- 效率：是否有明确的重复计算、N+1、循环远程调用或无意义集合转换；
- 抽象：是否引入单次使用层、万能帮助类、过度配置或不自然设计模式。

## 子 Agent 并发执行协议

本 Skill 被显式调用即代表用户授权在本次代码简化中使用只读子 Agent。环境支持子 Agent 时必须并发执行，不再额外询问是否启用。

1. 主 Agent 先冻结范围、读取完整目标文件和最小相邻上下文，再连续发起至少两个子 Agent `spawn` 请求；全部请求被调度器接受前，不得对任何子 Agent 执行 `wait` 或 `read`。`queued` 或 `running` 均视为成功启动。
2. 不含主 Agent 的并发子 Agent 槽位允许时启动四个子 Agent，分别负责复用、简化、效率、抽象。最多只能启动三个时，由第三个合并“效率 + 抽象”；最多只能启动两个时，分别合并为“复用 + 抽象”和“简化 + 效率”。不得遗漏任何视角，也不得用单个子 Agent 冒充并发。
3. 每个子 Agent 只读分析同一冻结范围，并按固定结构返回 `status`、`covered_views`、`candidates` 和 `blocked_reason`；每个候选包含候选 ID、位置、视角、代码证据、行为风险、最小建议和建议优先级。`status=completed` 且 `candidates=[]` 表示已完成检查但没有候选，属于有效结果。禁止编辑文件、运行破坏性命令或扩张范围。
4. 子 Agent 运行期间，主 Agent 可并行完成验证基线、真实调用链和最终数据源核验；不得在候选尚未汇总和复核前提前修改代码。
5. 主 Agent 必须复核候选位置和证据，去重后决定“自动修改”“P0/P1/P2 推荐修改”或“驳回”；只有主 Agent 可以统一编辑和验证。
6. 环境没有子 Agent 能力、并发容量不足两个、启动失败或结果不完整时，禁止静默降级，也不得自动修改文件。改为只读收口，明确列出并发阻塞原因、已完成范围和重新执行条件。

## 修改边界

- 只应用证据充分、行为保持、可以验证的安全简化。
- 保持接口契约、数据范围、异常语义、调用顺序、事务和并发行为不变。
- 保留既有注释；代码移动时同步移动相关注释，不清理无关注释。
- 不寻找或修复业务 Bug、安全漏洞或未确认逻辑问题；发现后报告并建议使用 Review 或调试流程。
- 不把个人风格偏好扩展到未修改历史代码。

## 高收益大范围自主修改

应用模式允许自主实施修改量较大的简化。不能只看文件数、改动行数或“跨文件”标签判断风险；关键是收益证据、行为等价证据和验证闭环。

这里的“自主”仅表示不因改动规模重复请求批准，不覆盖用户当前的只读或范围限制、仓库级 `AGENTS.md`/项目规范门禁、外部系统审批和破坏性操作审批。存在更高优先级约束时先遵守约束，并在汇总中写明。

只有同时满足以下门禁才可进入该路径：

1. **收益明确**：至少满足一项——通常有不少于 3 处已证明等价的重复实现；能明确消除批量链路中的重复 DB/RPC/API 调用或重复计算；能复用已存在且语义完全等价的稳定能力；能显著减少重复分支和后续同步维护点。减少远程或数据访问调用前必须证明调用只读或无副作用，并核对缓存一致性和取数时机。单纯减少行数或改写风格不算高收益。
2. **行为等价**：沿真实调用链核对最终数据源和关键参数，区分历史 Guard 条件与真实业务依赖，并证明接口、返回结构、数据范围、异常、权限、调用顺序、事务、并发、时序和外部副作用不变。
3. **范围闭合**：所有写入都来自已核验候选。若完成候选必须修改原冻结范围外的最小闭环文件，先列出新增文件及原因并重新冻结范围；未列入重新冻结范围的文件不得写入。不得覆盖或丢失与候选无关的用户已有改动，也不得顺带清理无关历史代码。
4. **抽象克制**：可以为不少于 3 个等价使用点提取归属自然、边界稳定的小型共享能力；不得借机改变模块职责、公共契约、依赖注入或生命周期边界，也不得创建单次使用层。
5. **验证充分**：修改前基线可执行且结果已记录；聚焦测试、编译或静态检查能够覆盖关键行为。缺少关键验证条件时，即使预估收益高也不得自主修改。

### 量化判定

硬门禁决定“能不能改”，评分只决定“是否值得大范围自主修改”。任何硬门禁失败都不能用高分抵消。

按 `调整后 ROI = 收益分 ÷ max(修改成本分, 1) × 证据置信度` 计算：

- **收益分 B（0–10）**：等价重复与复用 0–3，运行时调用/计算减少 0–3，维护点减少 0–2，已有稳定能力复用 0–2。
- **修改成本分 C（0–10）**：写集规模 0–2，边界复杂度 0–3，新增抽象 0–2，验证与恢复成本 0–3。
- **证据置信度 E**：只有静态代码证据为 0.5；代码证据加聚焦测试为 0.75；再有模块或完整相关测试为 0.9；再有运行指标或基准为 1.0。

每一项得分必须附文件位置、调用链、测试或指标证据；同一证据不得在多个维度重复计分。评分按可独立实施和验证的候选组或批次分别计算，高收益批次不得补贴未达阈值的其他批次。大范围自主修改的每个批次都必须同时满足：

```text
全部硬门禁通过
B >= 7
E >= 0.9
B / max(C, 1) * E >= 1.5
至少两个只读子 Agent 独立评分一致
```

四视角候选合并并划分候选组后，主 Agent 把每个候选组及其证据发送给至少两个子 Agent 并发独立评分，评分时不得互相查看结论。每个评分返回硬门禁、B、C、E、调整后 ROI 和逐项证据。若任一硬门禁结论不同、B 或 C 的最大差值超过 1 分、E 的最大差值超过 0.1，禁止通过平均分强行进入自主修改；主 Agent 先回到代码和测试消除证据分歧，再重新评分。评分一致时采用保守聚合：`B = min(Bi)`、`C = max(Ci)`、`E = min(Ei)`。阈值判断使用未四舍五入的原始结果，不能把低于 1.5 的 ROI 显示或进位成 1.5 后放行。

通过门禁后按候选组分批实施，每批都记录涉及文件、收益证据、行为等价证据和验证命令；先应用一批并运行聚焦验证，成功后再继续下一批，最后运行完整相关验证。某批失败、行为证据被推翻、写集与用户改动冲突或实际收益明显低于预期时，立即停止后续批次；只修复或还原本 Skill 在当前批次产生的改动，不使用破坏性 Git 命令，并把剩余候选转为 P1/P2 推荐。若各批聚焦验证通过但最终完整相关验证失败，不得声明完成；定位跨批次交互，修复或还原本 Skill 涉及的冲突批次，重新通过完整验证后才能交付成功。

## 验证

修改前记录原验证信号；修改后使用同一组命令和判定口径运行聚焦测试、编译或静态检查。高收益大范围修改还要保留逐批验证和最终完整相关验证。验证失败时回到当前简化批次定位，不用破坏性 Git 命令丢弃用户改动。

## 可选记录

如果用户把本次简化关联到某个 ZSTT 需求，可将摘要写入：

```text
<feature-dir>/auxiliary/code-simplification-YYYYMMDD-HHmm.md
```

记录范围、实际修改、保持不变的行为和验证结果。未关联需求时不强制创建 `.zstt` 文档。

## 输出

最终答复必须使用以下结构，不得把已修改项和未修改建议混在一段叙述中：

### 1. 执行概览

列出模式、冻结范围、最小相邻上下文、子 Agent 启动数/完成数/分工、四视角覆盖、并发是否成功、验证基线。若进入高收益大范围自主修改路径，还要列出改动规模预估、收益证据、硬门禁结论、两个子 Agent 的独立评分、保守聚合后的 B/C/E、调整后 ROI 和批次划分。

### 2. 已修改

每项使用 `A-xx` 编号，并分别写明：

- 位置；
- 修改了什么；
- 为什么修改；
- 收益证据；大范围修改时必须量化重复点、调用减少、维护点减少或其他可核验收益；
- 高收益大范围修改时列出评分证据和调整后 ROI；
- 行为保持依据；
- 所属批次；
- 验证结果。

没有自动修改时明确写“无”，并说明总体原因。

### 3. 推荐修改（未自动修改）

必须按 P0、P1、P2 三个小节依次输出，每项使用 `R-xx` 编号，并分别写明：

- 位置；
- 推荐怎么改；
- 推荐修改的原因；
- 没有自动修改的原因；
- 证据或影响；
- 建议下一步。

某个级别没有项目时明确写“无”。不要把误报、纯风格偏好或证据不足到无法形成方向的候选包装成推荐项。

优先级含义：

- P0：已确认的正确性、安全、数据、兼容或核心链路高风险，需要独立修复；本 Skill 为保持行为不自动修改。
- P1：收益明确且应处理，但无法证明契约、数据范围、事务、并发或模块边界保持不变，或缺少关键验证；有具体证据但尚待专项诊断的疑似 Bug/安全问题也归入 P1。跨文件或修改量大本身不构成 P1。
- P2：非阻塞且方向明确的维护性清理，但超出冻结范围、缺少充分验证或更适合后续单独处理；报告模式下已证明安全的候选也归入 P2，并写明是用户要求只读，而非技术风险。

没有自动修改的原因必须具体使用“报告模式（用户明确限制只读）”“可能改变行为”“证据不足”“评分不一致或未达到自主修改阈值”“收益不足以覆盖修改与回归成本”“超出冻结范围”“缺少验证条件”“疑似 Bug/安全问题”“与用户改动冲突”或“并发能力不足”等可核验原因，不能只写“风险较高”。

### 4. 验证与边界

列出修改前后相同命令的结果、最终 diff 范围、注释保留和 UTF-8 无 BOM 检查。高收益大范围修改还要列出每批结果、最终完整相关验证和实际收益；报告模式或并发阻塞时明确哪些验证未执行以及原因。

- 没有可自动修改项时明确报告已完成的检查和未修改原因，不为制造产出而改代码。
- 如创建辅助记录则给出路径。不要推荐或自动触发固定流程下一阶段。
