# ZSTT Code Simplification

## 定位

对用户指定范围做行为保持型简化。它不属于固定流程，不推进、不回退也不修改 `.zstt/meta.json`，可在实现中、Review 后或独立维护时使用。

仅当用户明确指定本 Skill 时执行。

开始前运行 `python .zstt-kit/runtime/rule_resolver.py resolve --skill zstt-code-simplification`，以 UTF-8 完整读取返回的规则 `path`，并记录规则集版本、指纹、规则 ID 和原因；解析失败或规则缺失时停止并执行 `zstt check --here`。随后读取 `references/advanced-playbook.md`。冻结范围并读取完整文件后，只按真实行为面追加 `data-access`、`concurrency`、`abstraction` 或 `design-patterns` 等上下文并重新解析，不能只凭文件名或关键词选规则。

## 范围选择

优先级：

1. 用户指定的文件或符号；
2. 用户指定提交或提交范围；
3. 当前 diff（未暂存和已暂存）；
4. 工作区干净且用户未指定范围时，使用最新提交。

指定符号时读取完整文件和相关调用方，不只看搜索片段。开始前固定范围，避免清理扩散。

## 模式与检查强度

1. 用户要求“只看”“只评审”或“不要修改”时进入报告模式；只交付候选、等价证据、跳过原因和验证建议，不写文件，也不重复执行修改前后验证。
2. 其他明确简化请求进入应用模式；修改前记录验证基线，只直接应用通过行为等价核验的安全候选。
3. 单个符号或单文件属于窄范围：四视角合并为一次检查，每个发现标注所属视角，不输出四份重复报告，也不为填矩阵扩读无关上下文。
4. 提交、diff 或多文件范围使用完整候选清单，先去重和核验，再统一应用或报告。
5. 无论范围大小，四视角都必须覆盖；检查强度只决定组织方式和证据深度，不降低接口、异常、数据范围、事务或并发门禁。

## 停止与冲突边界

- 用户明确指定的文件或符号无法定位、读取时，报告已探测位置、能力限制和所需最小路径或权限后停止；不得静默改用当前 diff 或最新提交。
- 冻结范围不包含用户请求检查的代码时，以空结果收口，不扩展到范围外寻找可改内容。
- 四视角检查后没有可自动修改项时，“已修改”明确写“无”，但仍须输出全部有效推荐；只有既无自动修改项、也无有效推荐项时才算真正空结果。
- 请求同时包含“只评审”和“直接修改”等冲突授权时，先按报告模式完成只读检查并请求用户确认；获得明确修改授权前不写文件。
- 若在四视角检查前因目标不可用或空范围停止，输出中将各视角标为“未执行/不适用”并说明原因，不得声称已经覆盖。

## 检查角度

- 复用：是否重复已有工具、查询、转换或公共能力；
- 简化：是否存在不必要分支、嵌套、临时变量或重复判断；
- 效率：是否有明确的重复计算、N+1、循环远程调用或无意义集合转换；
- 抽象：是否引入单次使用层、万能帮助类、过度配置或不自然设计模式。

四个视角必须独立检查后再由主上下文去重和核验。只有用户明确要求或批准时才可使用只读 Codex 子任务做可选并行分析；所有文件修改仍由主上下文统一应用。

## 修改边界

- 只应用证据充分、行为保持、可以验证的安全简化。
- 保持接口契约、数据范围、异常语义、调用顺序、事务和并发行为不变。
- 保留既有注释；代码移动时同步移动相关注释，不清理无关注释。
- 不寻找或修复业务 Bug、安全漏洞或未确认逻辑问题；发现后报告并建议使用 Review 或调试流程。
- 不把个人风格偏好扩展到未修改历史代码。

## 验证

修改前记录原验证信号；修改后使用同一组命令和判定口径运行聚焦测试、编译或静态检查。验证失败时回到简化点定位，不用破坏性 Git 命令丢弃用户改动。

## 可选记录

如果用户把本次简化关联到某个 ZSTT 需求，可将摘要写入：

```text
<feature-dir>/auxiliary/code-simplification-YYYYMMDD-HHmm.md
```

记录范围、实际修改、保持不变的行为和验证结果。未关联需求时不强制创建 `.zstt` 文档。

## 输出

最终答复必须使用以下结构，不得把已修改项、未修改建议和被驳回候选混在一段叙述中。

### 1. 执行概览

列出模式、冻结范围、实际读取的最小相邻上下文、四视角覆盖情况和验证基线。

### 2. 已修改

每项使用 `A-xx` 编号，并分别写明：

- 位置；
- 修改了什么；
- 为什么修改；
- 行为保持依据；
- 验证结果。

没有自动修改时明确写“无”，并说明总体原因。

### 3. 推荐修改（未自动修改）

必须按 P0、P1、P2 三个小节依次输出，每项使用 `R-xx` 编号，并分别写明：

- 位置；
- 推荐怎么改；
- 推荐修改的原因；
- 没有自动修改的原因；
- 证据或影响；
- 建议下一步。

某个级别没有项目时明确写“无”。优先级含义：

- P0：已确认的正确性、安全、数据、兼容或核心链路高风险，需要独立修复；本 Skill 为保持行为不自动修改。
- P1：收益明确且应处理，但无法证明接口、数据范围、异常、事务、并发或模块边界保持不变，或缺少关键验证；有具体证据但尚待专项诊断的疑似 Bug、安全问题也归入 P1。
- P2：非阻塞且方向明确的维护性清理，但超出冻结范围、当前验证不足或更适合后续单独处理；报告模式下已证明安全的候选也归入 P2，并写明是用户要求只读，而非技术风险。

没有自动修改的原因必须具体使用“报告模式（用户明确限制只读）”“可能改变行为”“证据不足”“超出冻结范围”“缺少验证条件”“疑似 Bug/安全问题”或“与用户改动冲突”等可核验原因，不能只写“风险较高”。误报、纯风格偏好或证据不足到无法形成方向的候选直接驳回，不包装成推荐项。

### 4. 验证与边界

列出修改前后相同命令的结果、最终 diff 范围、注释保留和 UTF-8 无 BOM 检查。报告模式下明确哪些验证未执行以及原因。

- 没有可自动修改项时明确报告已完成的检查和未修改原因，不为制造产出而改代码。
- 如创建辅助记录则给出路径。不要推荐或自动触发固定流程下一阶段。
