# Bug 排查与修复高级手册

## 1. 受理与最小补问

先建立问题卡：实际现象、预期结果、频率、最近发生时间、环境、项目、版本和关键标识。关键标识优先级通常为 `traceId`、业务主键、用户 ID、任务/订单/记录 ID、接口路径、请求响应和截图。

每轮只补问会改变下一步排查路径的信息。问题可以从源码、配置或现有日志确定时直接取证，不让用户重复提供。

## 2. 产物和阶段

默认不创建任何 Bug 报告、排查文档、`.zstt/bugs/` 目录或其他留档文件，直接在当前任务中维护证据并向用户交付结论。用户只要求排查、定位或修复不等于要求文档；只有用户明确要求生成、保存或留档时才使用 `assets/bug-report-template.md` 创建文件。

需要文档时，阶段只使用：

- `diagnosis`：正在排查，只允许只读证据和可复现验证；
- `awaiting_confirmation`：已交付根因和方案，等待用户二次确认；
- `fixing`：用户已明确授权最小代码修复；
- `verified`：修复和风险相称的验证已经闭环；
- `blocked`：缺少关键环境、权限、数据或无法隔离用户改动。

用户明确要求文档且关联 Full/Quick 需求时，把报告放到该需求 `auxiliary/bugs/`；明确要求文档的独立问题放到 `.zstt/bugs/`。报告不创建或修改固定流程 `meta.json`，也不代表发布完成。

## 3. 能力探测与环境安全

开始时记录源码、Git、CodeGraph、日志、MySQL、ES、Redis、MQ、测试环境和构建工具是否可用。

测试/本地环境确认目标后可执行只读查询。线上环境默认只生成查询，让用户或有权限的平台执行并回传脱敏结果。任何写数据、缓存删除、消息重放、任务补偿或写接口都属于独立高风险动作，必须说明精确对象、影响、恢复方式并获得单独授权。

查询遵循：

- 每条查询先写明要回答的问题；
- 使用业务主键或有限时间范围；
- 只选择必要字段，稳定排序并限制返回数量；
- ES DSL 设置 `size` 和时间范围；
- 不做无边界全表、全索引扫描；
- 不在命令、报告或聊天中回显凭证。

## 4. 真实调用链与数据源

从用户可观察入口开始，依次追踪 Controller/Job/Consumer、Service/Manager、Facade/Client、Repository/Mapper/SQL、缓存/ES/MQ和相关横切逻辑，直到最终结果来源。

对每个影响结果的字段记录：输入来源、转换条件、最终赋值、持久化位置、读取来源和返回位置。入口判空、历史 Guard 或相似字段不能自动当作真实业务依赖。

优先检查以下常见模型，但只能作为调查假设：

1. 同一请求写后读使用两套状态源；
2. 事务未提交就发送消息或被下游读取；
3. MQ、ES或异步落表造成短暂展示滞后；
4. DB已更新但缓存未失效或Key维度错误；
5. 状态、进度、结果分别来自不一致的数据范围；
6. 重复提交、幂等分支、重试或乱序覆盖新状态；
7. 环境、项目、库、索引或租户选择错误；
8. 循环远程调用、N+1、超时或连接资源导致偶发失败。

## 5. 证据与根因门禁

为每个候选原因维护证据：

| 假设 | 代码证据 | 数据/日志证据 | 时间线 | 反证 | 结论 |
|---|---|---|---|---|---|

根因结论至少回答：什么条件触发、哪段逻辑造成什么状态、为什么形成用户现象、影响哪些对象。只有代码推断时写“高/中/低置信度假设”，并给出最小验证动作。

发现多个独立问题时分别编号，区分主根因、放大因素和无关历史问题。不要因为测试变绿、日志有异常或数据看起来不一致就跳过因果链。

## 6. 排查交付与确认门禁

排查结论按固定顺序输出：

1. 现象与触发条件；
2. 根因或待验证假设；
3. 代码、数据和时间线证据；
4. 影响范围；
5. 最小修复方案及不做事项；
6. 风险、验证和回归点；
7. 是否等待用户确认修复。

用户最初的“修复这个 Bug”不能同时充当二次确认。只有结论交付后的明确回复才解锁修复；在当前任务上下文中保留确认来源，只有用户明确要求文档时才写入报告。

## 7. 修复适用边界

适合在本 Skill 内修复：错误条件、空值边界、错误字段来源、明确的缓存失效遗漏、局部异常处理、已确认契约内的最小实现偏差。

以下情况转入 ZSTT Full/Quick：新增业务能力、接口或消息契约变化、表结构/索引/SQL口径变化、核心状态机或权限变化、跨服务重构、大范围兼容和发布迁移。涉及 SQL 设计时必须使用技术方案阶段 SQL Gate。

## 8. 安全修复与验证

修复前记录 Git 基线、目标文件完整上下文、用户已有改动、失败信号和允许修改范围。无法隔离既有改动时停止，不自动清理工作区。

实施时保持最小闭环：失败信号、最小实现、局部验证、完整 diff 复核、相邻回归。检查日志是否包含必要业务身份和异常堆栈且不泄密，检查事务和异步顺序、N+1、循环远程调用、Jackson兼容及既有注释。

修复后向用户交付：实际文件与符号、修改前信号、验证命令和退出码、实际结果、未验证边界、主场景和相邻场景回归点。未运行的测试不得写成通过；只有用户明确要求文档时才同步到报告。

## 9. 用户纠正

用户提供新的 trace、日志、SQL结果、截图或指出旧判断错误时，立即刷新证据表。旧根因被推翻时明确记录原因，不通过增加 fallback 保住原结论。
