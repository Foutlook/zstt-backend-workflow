# ZSTT Bug Fix

## 定位

处理独立的缺陷定性、问题排查、只读数据查询和 Java 后端最小修复，不属于 Full/Quick 固定阶段，也不修改工作流 `meta.json`。固定原则是：先确认目标，再用最短证据路径判断是否存在真实或可达的契约违反；只有支持缺陷后才分析责任和最小修复。纯数据查询按用户意图直接交付，不强行进入缺陷流程。

用户第一次要求“修复 Bug”只授权形成确认卡和只读取证，不代表缺陷已经成立或已经批准代码修改。只有支持缺陷、用户看到根因、证据、影响和方案后明确回复“继续修复”“按这个方案修”等，才进入修复阶段。

## 角色选择

本 Skill 只有两个角色，查询数据是两种角色共有能力，不是第三种模式：

- **开发角色**：适用于用户明确以开发身份处理，或当前存在业务代码且用户要求代码级定位或修复。联合代码、日志、Trace、MySQL、ES 和时间线取证；排查结论得到二次确认后可以进入最小代码修复。
- **测试角色**：适用于用户明确以测试身份处理，或当前没有业务代码。只依赖可用的日志、Trace、MySQL、ES、接口响应和用户证据完成问题定位或数据查询；不要求 Git 仓库，不把代码不可用写成阻塞，不进入代码修复。

优先采用用户明确指定的角色。用户未指定时，有业务代码且要求代码级定位或修复则选择开发角色；没有业务代码则选择测试角色。仅当当前能力和用户意图仍无法判断时，询问“本次按开发角色还是测试角色处理？”。开始取证前向用户说明已选择的角色和能力边界。

## 开始前

1. 完整读取 `references/runtime-bootstrap.md`，跨平台解析可用的 Python 3.11+ 启动器和 `.zstt-kit` 绝对路径。某个命令名或候选路径不存在时继续兼容探测；不得因存在 `python3` 但没有 `python`、没有全局 `zstt` 命令或当前目录不是安装根目录而询问用户或停止。
2. 使用解析出的启动器和 Kit 绝对路径运行 `runtime/rule_resolver.py resolve --skill zstt-bug-fix`，完整读取返回的规则，记录 `rulesetVersion`、`rulesetFingerprint`、规则 ID 和原因。项目内解析器存在时不要求全局安装 `zstt`；只有解析器实际返回规则或清单错误时才按启动指南执行 CLI 降级检查。
3. 完整读取 `references/advanced-playbook.md`。
4. 问题包含 Trace ID、日志、服务异常或明确时间窗口时，完整读取 `references/observability-mcp.md`；按环境和后端/客户端意图优先读取已解析 Kit 中 `project-databases.json` 对应的 `$testBackendSls`、`$testClientSls`、`$prodBackendSls`、`$prodClientSls`，配置完整时直接查询，不重复发现 Project 和 Logstore。
5. 使用 Observability、MySQL 或 ES 凭据前，完整读取 `references/environment-config.md`；数据库名与测试 SLS 映射先按其中规则读取已解析 Kit 中的 `project-databases.json`，确认目标环境和后端/客户端凭据 Scope。`$productionSameAsTest` 只确认生产与测试库名相同，不授权连接生产库，生产凭据仍禁止回退到测试配置。
6. 开发角色根据真实代码链路追加 `data-access`、`transaction`、`concurrency`、`jackson`、`sql-design` 等上下文并重新解析；不得只凭类名或现象加载规则。测试角色不加载只服务于代码修改的规则。
7. 默认不创建 Bug 报告、排查文档、`.zstt/bugs/` 目录或其他留档文件。只有用户明确要求“生成报告”“保存排查记录”“需要文档”等文件产物时，才使用 `assets/bug-report-template.md` 创建；普通的排查、定位或修复请求不构成文档创建授权。
8. 开发角色在当前任务上下文中确认 Git 基线、用户已有改动和未跟踪业务文件。测试角色只记录可用的数据源和权限，不要求 Git 基线。排查阶段默认只读，不把用户已有改动归因于本轮。

## 第一阶段：缺陷定性与证据化排查

### 1. 确认问题边界

纯数据查询只确认角色、查询对象、筛选条件、所需字段或统计口径，然后直接进入只读取证，不执行缺陷确认门禁。

问题排查先形成一个用户可校正的缺陷确认卡，包含：精确目标和边界、报告的实际行为及其证据状态、预期行为及依据、可测试差异、环境、已知时间/身份/版本/项目锚点，以及本次只读调查和可能的最小修复交接边界。用户未确认该卡前停止，不查询日志、数据库或代码，也不把报告写成已确认缺陷。

确认卡只锁定调查目标和唯一的 `test`、`prod` 或明确的本地环境，不证明事件发生、缺陷成立、技术身份、根因或修复方案。用户不知道的 Trace、日志、数据库行、仓库、分支、提交、服务和源码位置属于调查需要定位的技术信息，不要求用户猜测。

信息不足时每轮只询问最影响下一步的 1–5 项；能从当前上下文确认的内容不重复询问。目标、环境或预期依据发生实质变化时重新确认卡片；普通技术锚点补充不需要重复确认。

测试库名优先从已解析 Kit 的 `project-databases.json` 按当前项目相对路径匹配；没有匹配、匹配冲突或项目归属不明确时必须确认，不能猜测后写成事实。用户确认的新映射可以建议补入该文件，但未经用户要求不得修改配置。

### 2. 按环境取证

- 测试或本地环境：确认目标后可以执行只读 MySQL、ES、日志、编译和测试；查询必须按关键 ID 或时间范围收敛，大表查询限制数量。
- 线上环境：默认不直接连接线上数据库、ES 或执行写操作；基于真实调用链向用户提供只读 SQL、ES DSL、日志筛选条件和需要回传的字段。用户明确指定生产环境且存在对应 `$prodBackendSls` 或 `$prodClientSls` 时，可以使用匹配的生产 AK Scope 执行只读日志查询；不得回退到测试 AK。仅当映射文件明确声明 `$productionSameAsTest: true` 时，才可在生产只读 SQL 中使用已匹配的库名；否则使用待确认占位或先询问用户。
- 本地命令需要凭据时，只通过已解析 Kit 的 `runtime/with_env.py` 绝对路径，使用启动指南确定的同一 Python，按 `test|prod` 和 `observability|observability-client|mysql|es` Scope 注入；测试客户端日志只用 `observability-client`，禁止读取后回显、跨 Scope 复用或把生产缺失降级为测试。
- 任何环境都不得在回复或用户明确要求的文档中泄露完整 Token、Cookie、Authorization、账号或密码。
- 未经用户明确授权，不执行 `INSERT`、`UPDATE`、`DELETE`、数据修复、消息重放、缓存删除或线上写接口。

### 3. 日志与 Trace MCP 取证

- 有 Trace ID 时先查完整 Trace 和 Span，再按失败服务、Span 时间窗口查询日志；不要先做无边界关键词扫描。
- 无 Trace ID 时按接口、业务 ID、Pod/服务名和分钟级时间范围查询入口日志，再从结果提取 Trace ID 回查链路。
- 优先使用 `umodel_get_traces`、`umodel_search_traces`、`sls_execute_sql` 和 `sls_get_context_logs`；当前环境存在有效后端/客户端 SLS 映射时按意图直接使用，其他项目、Logstore、Workspace 或 TraceSet 未知时只做一次收敛式发现。
- MCP 查询和结果都不得包含完整 Token、Cookie、Authorization、AccessKey、Secret 或密码；对外输出前再次脱敏。
- MCP 未注册、鉴权失败或数据源不覆盖目标环境时，记录能力缺口，并给出可由用户执行的精确查询条件，不把“查不到”写成“不存在”。

### 4. 建立真实问题链路

- 开发角色按问题实际经过的路径检查入口、Service/Manager、Facade/Client、Repository/Mapper/SQL、缓存、ES、MQ、异步任务，以及直接影响入参、权限、路由、事务和状态的配置或横切逻辑。追到最终查询、计算、赋值、持久化或外部调用点，区分 Guard 条件和真实业务依赖。
- 测试角色按客户端请求、入口日志、Trace/Span、上下游服务、MySQL、ES、缓存/MQ 可见状态和接口返回建立运行时链路。能够定位失败服务、异常阶段或数据不一致点时直接交付；无法看到代码内部原因时明确标为开发待确认，不把没有源码写成无结论。

只把必经链路或有直接证据的横切逻辑纳入结论；相似代码和搜索未命中都不能直接证明根因或不存在。

### 5. 建立证据链

至少整理：

- 代码证据：开发角色记录具体文件、符号、条件和数据来源；测试角色没有代码时标为不适用；
- 数据证据：日志、MySQL、ES、接口响应中的字段、状态和时间；
- 过程证据：请求、写入、事务提交、缓存/MQ/ES 更新和返回展示的时间线。

测试角色的结论可以停在失败服务、异常阶段、数据不一致点或高置信度运行时原因，并给开发人员提供精确的 Trace、时间窗口、服务、状态和待核对点。没有运行数据或日志佐证时，将结论标为“推测”或“待验证”，不得写成已证明根因。用户补充新证据时刷新结论，必要时明确推翻旧判断。

### 6. 缺陷确认门禁

用能够决定问题性质的最短证据路径判断是否同时成立：

1. 存在适用于当前目标和版本的产品、接口、数据或实现契约；
2. 存在真实观察到的状态，或静态证据证明能够到达的实现路径；
3. 实际或可达行为与契约之间存在可测试差异；
4. 该差异需要工程纠正，而不是使用方式、环境限制、产品设计或证据误读。

用户报告、测试用例和异常日志本身都不能单独证明缺陷。运行时发生是强证据但不是唯一途径；适用版本的明确可达代码路径也可以确认缺陷。反之，有异常但没有适用契约，只能说明异常事实，不能直接确认 Bug。

确认后锁定契约、真实或可达状态、测试差异、纠正需要和影响边界。后续普通的深层原因不确定、仓库定位困难或无关查询无命中不能推翻该基线；只有直接反证才能重新打开缺陷确认。

缺陷确认只允许三种结果：

- **支持缺陷**：四项条件均有证据支持，进入责任、根因和最小修复分析；
- **支持非缺陷**：证据直接表明适用契约未被违反或无需工程纠正，交付解释后停止；
- **有界未解决**：所有当前授权且能够改变结论的路径已读取、判定不适用或具体不可用，但仍不能确认或排除契约违反；交付缺口和恢复条件后停止。

零命中、超时、未索引、权限不足或一个来源不可用不是支持非缺陷的证据，也不能替代仍然可执行的其他决定性路径。

### 7. 收敛责任和最小修复

只对“支持缺陷”继续。此时把取证目标从“让缺陷更确定”切换为：适用纠正契约、问题状态如何产生和传播、哪个边界负责纠正、最小修复是什么、哪些行为必须保持、如何验收和验证。

区分用户表面现象、直接失败机制、传播与处理、深层原因和最终修复责任。第一个报错组件、最先出现异常日志的服务或局部判空都不能自动成为修复负责人。所有会改变修复负责人或最小修复的分支必须有证据回答、证明不适用，或说明具体不可用及其影响。

开发角色只有在责任边界、最小修复、保持不变行为、验收方式、验证设计和风险足以稳定交接时，才能给出修复方案并进入二次确认。证据不足以稳定负责人或最小修复时，即使缺陷已经成立，也应以“有界未解决”交付，不得编造修复方案。

### 8. 交付排查结论并停止

纯数据查询直接交付查询目标、环境、数据源、筛选口径、脱敏结果、空结果或数据质量说明，然后结束；不得强行扩展为 Bug 根因分析或代码修复。

支持非缺陷时，交付适用契约、实际或可达行为、决定性反证、为什么无需工程纠正、适用范围和限制，不生成根因、修复方案或确认门禁。

有界未解决时，区分已确认事实、仍会改变缺陷或责任判断的分支、已执行读取、具体不可用证据和系统侧恢复条件，不要求用户猜测技术信息，不生成不稳定的修复方案。

支持缺陷时，交付锁定的缺陷确认基线、触发条件、直接机制、根因或受支持的责任说明、证据、影响范围、最小修复、保持不变行为、验收与验证设计、风险和回归点。测试角色同时给出开发交接所需的 Trace、服务、时间窗口和待核对点，交付后结束，不进入代码修复。开发角色等待用户明确确认，禁止修改业务代码。除非用户明确要求文件产物，否则只在当前任务中输出结论，不创建或更新任何报告文件。

开发角色发现根因要求新增需求、改变接口契约、DDL/索引/SQL 口径、核心状态、权限、事务语义或跨服务协议时，停止 Bug 快修并建议进入 ZSTT Full/Quick 对应阶段；不得以 Bug 修复名义绕过设计和 SQL Gate。测试角色只记录该变化需求和证据，交给开发流程确认。

## 第二阶段：开发角色确认后的最小修复

测试角色没有本阶段。只有缺陷确认结果为“支持缺陷”，且开发角色获得完整排查结论之后的用户明确确认，才执行以下步骤：

1. 确认用户是在看到排查结论后明确授权修复，并在当前任务上下文中保留确认来源、修复范围、风险和验证方式；若用户明确要求了报告，再同步更新报告。
2. 重新检查 Git 状态和完整目标文件；不自动 `pull`、切换分支、stash、reset、提交或覆盖用户改动。需要新分支或新基线时先遵循仓库规则并向用户说明。
3. 先建立失败信号或可复现证据，再做最小改动；禁止无关重构、整片格式化、推测性 fallback 和临时排查代码遗留。
4. 按动态 Java Rules 检查注释、日志、异常、事务、Jackson、N+1、循环远程调用、兼容和数据源一致性。
5. 使用修改前后的同一口径完成聚焦验证；至少执行与风险相称的编译、单测、接口、SQL/状态回查或关键链路验证之一。
6. 向用户交付实际文件、验证命令、退出码、结果、未验证边界和回归点；若用户明确要求了报告，再同步更新报告。只有修复和关键验证闭环后才视为已验证。

发现修复方案与排查结论不一致、需要扩大范围或会覆盖用户已有工作时立即停止，重新交付偏差和新方案，等待再次确认。

## 输出与边界

- 等待目标确认：只输出缺陷确认卡和一个确认问题，不开始取证。
- 支持非缺陷：输出适用契约、实际行为、决定性反证、范围和限制；不生成修复方案。
- 有界未解决：输出当前证据、关键缺口、已关闭路径和恢复条件；不编造根因或修复。
- 支持缺陷的测试角色：输出缺陷基线、运行时问题位置、证据、影响和待开发核对点；不要求代码，不进入修复。
- 支持缺陷的开发角色等待确认：输出缺陷基线、根因或责任说明、证据、影响、最小方案、验收验证和明确的修复确认门禁。
- 开发角色已确认修复：输出实际修改、验证结果、回归点和残余风险。
- 不自动执行固定流程下一阶段，不自动 commit、push、合并、部署、线上数据修复或消息重放。
