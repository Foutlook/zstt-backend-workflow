# ZSTT 需求与代码差异分析

## 定位

围绕一个有边界的新增或变更需求，把“需求希望怎样工作”和“最新代码及目标环境数据能力实际支持什么”逐项对齐。默认只读、只在当前任务中交付，不创建或修改 `00-requirement.md`、`01-research.md`、`02-design.md`、`.zstt/meta.json`，也不修改业务代码、配置、数据库或 Git 历史。

本 Skill 负责需求与现状之间的判定层：

```text
需求材料 → 原子需求与确认状态
最新代码与目标环境数据 → 当前行为、数据支持状态与证据
逐项对照 → 已一致、部分一致、确认差异、需求待确认、证据待补、不适用
已确认差异 → 确定变更范围与联动核查
```

它不同于：

- `$zstt-requirement-clarification`：将散乱、冲突或缺失的需求收敛为正式可实施契约；
- `$zstt-product-feature-analysis`：只解释已有功能，默认不与新增需求逐项判定差异；
- `$zstt-repo-research`：基于已完成的 `00-requirement.md` 生成 Full 阶段 `01-research.md`；
- `$zstt-bug-fix`：确认既有契约是否被违反，并在授权后诊断和修复缺陷。

## 开始前

1. 完整读取 `references/runtime-bootstrap.md`，解析 `{PYTHON}` 与 `{ZSTT_KIT}`。
2. 运行 `{PYTHON} "{ZSTT_KIT}/runtime/rule_resolver.py" resolve --skill zstt-prd-code-gap-analysis`。
3. 以 UTF-8 完整读取解析结果中每个规则的 `path`，记录 `rulesetVersion`、`rulesetFingerprint`、规则 ID 和选择原因。解析失败或规则缺失时停止，并执行 `zstt check --here`；没有全局 `zstt` 命令时使用当前可用的等价项目检查入口。
4. 读取项目 `AGENTS.md` 和用户授权的需求材料，锁定一个需求主题、目标读者、产品边界及相关仓库。
5. 需求涉及实际数据覆盖，且数据事实会改变差异结论或变更范围时，完整读取 `references/environment-config.md` 和 `references/dms-mcp.md`，并按 `{ZSTT_KIT}/project-databases.json` 解析项目与目标库。纯静态代码或与数据无关的问题不要求数据库环境。
6. 数据查询默认先锁定并验证 `prod`。只有生产验证因配置、映射、实例、权限、网络、超时或工具能力失败，无法形成生产数据事实时，才按同一查询目标回退到 `test`；不得并行查询两个环境。
7. 用户明确指定 `test` 时只查询测试环境，不先查生产；用户明确指定 `prod` 时只查询生产环境，不回退测试。默认生产查询和失败后的测试回退都必须保持只读、收敛、限量、脱敏，并分别记录环境与失败原因。

## 事实边界

始终分开记录：

- **原始需求事实**：材料或用户明确表达的内容；
- **已确认需求**：可以作为差异和变更判断依据的当前有效口径；
- **未确认需求**：歧义、冲突、缺失边界或尚未确认的推断；
- **当前实现事实**：适用仓库、分支和提交中的源码、配置或契约直接证明的行为；
- **当前数据事实**：Schema、写入链路、查询链路和指定环境中的有界观察分别证明的结构、产生方式、可访问性和覆盖；
- **运行时事实**：有明确环境、身份和时间范围的日志或数据观察；
- **分析推断**：由证据支持、但未被单一来源直接证明的关系。

需求材料不能证明功能已经实现，源码不能证明产品意图，表字段存在不能证明历史数据完整，一次样本不能代表总体覆盖，查询无结果也不能证明代码或数据不存在。

## 工作流

### 1. 锁定分析边界

确认需求主题、材料来源、角色、目标对象、产品范围、相关仓库及需要回答的问题。只有以下信息缺失到无法限定调查时才先提一个阻塞问题：

- 无法识别目标产品或功能对象；
- 多个仓库或版本会产生不同结论，且没有选择依据；
- 数据结论必需，但默认 `prod` 及允许回退的 `test` 无法解析到唯一项目数据库映射；
- 项目到数据库的映射缺失、冲突或无法唯一匹配；
- 关键材料不可读，导致核心行为无法提取。

其他歧义先登记为未确认项，同时继续调查可以确定的代码和数据事实。

### 2. 建立原子需求台账

将材料拆为可分别验证的 `R01`、`R02`……，每项只表达一个行为或约束，并记录来源、角色、对象、触发条件、期望行为、用户结果或副作用、数据对象与粒度、范围与例外、确认状态和确认来源。

确认状态只允许：

| 状态 | 判定 |
| --- | --- |
| `已确认` | 材料明确且内部一致，或用户已经明确确认 |
| `待确认` | 存在歧义、缺少边界或需要用户选择业务口径 |
| `冲突` | 两个有效来源给出互不兼容的口径 |
| `推断` | 为理解而提出，尚不能当作需求事实 |

不要用当前代码倒推产品需求，也不要把“通常如此”提升为已确认。

### 3. 确认最新代码基线

每个相关仓库都必须单独确认远程身份、目标分支、提交和实际读取来源：

1. 先执行 `git fetch --prune origin` 更新远程引用；失败时不能声称已确认最新分支。
2. 用户指定分支或版本时优先采用；否则只在 `origin` 下的 `release/`、`release-`、`bugfix/`、`bugfix-` 候选中，按可比较版本和尖端提交时间确定最新目标分支。没有候选或无法可靠排序时让用户选择，不自动退回默认分支。
3. 只有 `HEAD` 等于 `origin/<目标分支>`、待分析源码没有未提交修改，并能记录分支与提交 ID 时，才把本地工作树视为最新代码。
4. 本地不是最新代码时，优先使用当前会话已暴露的只读仓库 MCP / CodeGraph 读取远程目标分支；必须验证仓库身份、目标分支或提交、索引新鲜度和关键源码覆盖。
5. 远程读取不可用时，只有工作区完全干净、远程引用来自本次成功 fetch、同名本地分支可快进时，才在 commentary 中说明目标分支和提交后安全切换。禁止 stash、强制切换、reset、清理或覆盖用户修改。
6. 本地 CodeGraph 可用时检查索引与目标工作树是否一致，并在告知用户后按需更新 `.codegraph`；不可用时使用 `rg` 和源码阅读降级，不自行安装工具。

记录基线：

| 仓库 | 实际读取来源 | 目标分支 | 提交 ID | 最新性状态 | 局限 |
| --- | --- | --- | --- | --- | --- |

实际读取来源只能写已验证事实，例如“本地原有最新代码”“远程 MCP”“切换后的本地目标分支”。版本无法证明时，相关结论标记 `证据待补`，不得生成确定变更点。

### 4. 还原当前行为

按需求项从用户可观察入口追到最终行为点：

1. Controller、Job、Consumer、页面事件或真实入口；
2. Service、Manager、Facade、RPC/HTTP Client 的实际调用链；
3. Repository、Mapper、SQL、缓存、ES、MQ、配置、计算或最终赋值点；
4. 真正影响结果的参数、状态、时间、权限、租户和上下文；
5. 用户可见结果、持久化结果或外部副作用；
6. 有直接证据的调用方、消费者和影响边界。

CodeGraph 只作为导航证据，关键结论必须回到源码验证。Guard、判空和字段透传只用于定位，不能自动认定为真实业务依赖。列表、聚合、图表或映射补全场景必须核对最终实体集与 ownership、状态等映射的数据源范围是否一致。

### 5. 判断数据是否支持

需求涉及查询、筛选、统计、聚合、历史回溯、跨实体映射、数据写入或外部数据时，单独核对：

1. **结构支持**：表、字段、索引、枚举、事件、缓存或外部接口能否表达所需数据；
2. **链路支持**：是否存在真实生产、写入、更新、同步和读取路径，关键参数能否到达最终数据点；
3. **实际数据支持**：目标环境中的语义、粒度、时间覆盖、完整性、隔离维度和更新时效是否满足需求。

数据支持状态只允许：

| 状态 | 判定 |
| --- | --- |
| `支持` | 结构、链路和需求所需实际覆盖均有证据 |
| `部分支持` | 只支持部分对象、时间、范围、粒度或历史数据 |
| `不支持` | 有直接证据证明缺少结构、生产链路或所需覆盖 |
| `待补证` | 只能证明结构或代码路径，无法证明数据语义、覆盖或运行状态 |
| `不适用` | 需求不依赖业务数据能力 |

实际数据会改变结论时，按 `references/environment-config.md` 解析唯一项目映射，再按 `references/dms-mcp.md` 执行一个有边界的 `persistence-state` 只读取证。优先聚合和脱敏统计；仅在字段语义或关联必须查看样本时取最少行数和必要列。

`test` 只证明测试环境，`prod` 只证明生产环境。默认先取生产证据；仅当生产验证发生技术或访问失败、无法形成生产事实时，才允许用相同目标回退测试验证。生产查询成功但结果为空、数据不支持或覆盖不足，均属于生产数据事实，不视为失败，也不得用测试结果替代。两个环境的映射、凭据、实例、失败原因和结论必须分别记录。DDL 或 DTO 只能证明结构，写入代码只能证明存在生产路径，查询代码只能证明可以访问；它们都不能单独证明现有数据完整。

### 6. 形成需求—代码与数据追踪矩阵

每个原子需求必须且只能得到一个主结论：

| 主结论 | 使用条件 | 是否进入确定变更集 |
| --- | --- | --- |
| `已一致` | 需求已确认，最新代码和相关数据证据证明完整满足 | 否 |
| `部分一致` | 需求已确认，当前实现或数据只满足可分离的一部分 | 仅未满足且已确认部分 |
| `确认差异` | 需求已确认，最新代码或数据证据证明不一致 | 是 |
| `需求待确认` | 业务口径为待确认、冲突或推断 | 否 |
| `证据待补` | 版本、调用链、最终行为或数据支持证据不足 | 否 |
| `不适用` | 有证据证明不属于当前产品或仓库边界 | 否 |

矩阵至少包含：

| 需求 ID | 确认状态 | 期望行为 | 当前代码行为 | 代码证据 | 数据环境 | 数据支持状态与证据 | 主结论 | 差异或未确认点 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

确定变更点必须同时满足：需求口径已确认；代码证据来自适用最新版本；数据相关变更由 Schema、生产/读取链路或目标环境数据直接证明。已证明代码差异但数据仍待补证时，只确认代码侧变更，将数据侧列为 `联动核查`，不得顺带断言需要或不需要改表、补数或迁移。

### 7. 收敛未确认问题

将问题分为：

- `P0`：改变核心范围、权限、状态、数据身份、接口契约或验收，阻塞确定变更范围；
- `P1`：影响重要行为分支、兼容或异常处理；
- `P2`：影响次要交互、文案或非阻塞细节。

每个问题说明需求来源、已知代码或目标环境数据事实、需要确认的口径、影响原因和需求 ID。业务意图由用户确认；代码和可查询的数据事实继续由分析侧调查，不把“代码现在怎样”“库里有没有数据”反问给产品。

### 8. 形成已确认变更范围

仅对 `确认差异` 和 `部分一致` 中已确认的未满足部分输出：

- `确定需变更`：已由需求、最新代码和必要数据证据闭环的职责、规则或契约；
- `联动核查`：有影响迹象但仍缺少源码、Schema、环境数据或消费者证据的边界；
- `无需变更`：当前能力已经满足或有证据排除的范围。

只有源码已定位到具体文件、类或方法时才写具体落点；否则写职责级范围和最小补证动作。只说明“哪里、什么行为需要变化”，不决定具体实现，不生成架构方案、SQL 草案、任务拆分、工期、提交或代码修改。

## 输出契约

先给一句话总判断，再按实际需要提供：

1. 分析范围与证据基线：材料、仓库、实际代码来源、分支、提交、数据环境与局限；
2. 需求理解摘要：目标、角色、主流程和明确边界；
3. 需求—代码与数据追踪矩阵；
4. 待确认问题：P0/P1/P2、影响需求和确认原因；
5. 已确认变更范围：确定需变更、联动核查、无需变更；
6. 当前已支持能力，防止重复建设；
7. 证据缺口与解除未知所需的最小动作。

代码证据使用仓库、分支或提交、文件、符号和行号。数据证据说明 `test` 或 `prod`、Schema、表、选择条件、时间窗口和脱敏统计，不暴露连接信息、凭据或敏感记录。明确区分需求原文、代码事实、环境数据事实和分析推断。

## 停止与分流

- 材料散乱到无法建立稳定业务骨架时，交付已发现的问题并建议用户显式调用 `$zstt-requirement-clarification`。
- 用户要求正式 Full 仓库调研产物时，建议显式调用 `$zstt-repo-research`；本 Skill 不伪造阶段完成。
- 用户只需解释已有行为时，建议 `$zstt-product-feature-analysis`。
- 证据显示可能违反既有契约时，只陈述预期、实际、依据与缺口，并建议 `$zstt-bug-fix`；不在本 Skill 中确认或修复缺陷。
- 全部需求项已有主结论，或剩余未知无法通过有界读取解除时停止。
- 不自动执行推荐的下一阶段，不自动 commit、push、合并、发布或部署。
