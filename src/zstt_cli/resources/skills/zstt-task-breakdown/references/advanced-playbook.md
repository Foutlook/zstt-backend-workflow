# 高级任务拆分 Playbook

## 1. 目标

把 `00-requirement.md`、`01-research.md` 和 `02-design.md` 转成能直接排期、实现和验证的 `03-tasks.md`。`Txx` 只承接已确认的仓库编码改动，不重新发明需求、代码事实或技术方案。

接口明细、SQL、Claim Ledger 等 `auxiliary/` 附件是输入证据；权威设计仍是 `02-design.md`。附件与主方案不一致时先回到方案阶段修正。

## 2. 覆盖矩阵

拆任务前建立覆盖矩阵：

```markdown
| 来源类型 | 来源 ID/位置 | 要求或决策 | 对应任务 | 覆盖状态 | 缺口 |
|---|---|---|---|---|---|
```

来源规则：

- 每个 Txx 首先引用 `02-design.md`“代码改动落点”中的已确认核心 `Dxx`；
- 需求范围、禁止项和验收可补充引用需求条目；
- 调研结论、复用边界和旧链路风险可补充引用 `Cxx`；
- 接口、存储和测试代码策略补充引用附件，但附件不能单独产生 Txx；
- 辅助接口或 SQL 引用具体附件路径和主方案章节。

每个接口、SQL 文件/数据迁移脚本、配置、缓存、MQ 和旧链路防护都要映射到编码任务；人工 SQL、环境操作、联调协调、测试执行、测试报告、发布、灰度、监控和回滚映射到非编码交接事项。没有任务承接的核心改动是覆盖缺口；没有核心 `Dxx` 的任务是范围扩张。

## 3. 任务粒度

按能独立交付和验证的业务闭环拆分，不按 Controller、Service、Mapper 层机械切碎。推荐顺序：

1. 契约和前置条件；
2. 数据/SQL 文件/配置代码；
3. DTO、枚举和基础模型；
4. 核心业务实现；
5. 入口和跨仓库协作；
6. 任务内最小验证与非编码交接。

每个任务必须包含：

```markdown
- 任务 ID、目标、类型和所属仓库；
- 来源 Dxx（必填）以及补充的 Cxx/需求/附件；
- 所属 Git 项目或仓库；
- 预计修改文件或新增文件的精确路径；
- 接口、SQL、配置、缓存或消息范围；
- 明确不做事项；
- 前置/后续依赖和初始状态；
- 输出物和完成标准；
- 精确验证命令、预期信号和失败信号；
- 风险、阻塞点、协作方和并行等级。
```

任务初始状态只使用 `ready`、`pending`、`blocked`。依赖尚未完成 Txx 的任务必须是 `pending`；SQL、契约、用户确认或外部环境未满足时不得标记 ready。`blocked` 只用于任务定义已经完整、但存在外部执行条件的情况。

## 4. 关键路径与阻塞点

输出串行关键路径，例如 `T01 -> T03 -> T05 -> T08`，并说明每条边的依赖原因。

阻塞项必须包含：阻塞任务、原因、解除条件、责任方、重新验证动作。接口 Provider/Consumer、MQ 生产/消费、前后端契约、SQL 字段和配置口径未锁定时使用“先锁契约”，不能把两端同时标成可独立完成。

## 5. 并行等级

先判断 L0/L1/L2，再决定输出深度：

- **L0 不并行**：任务集中于同一主链、文件或契约，或规模小到并行收益低。写明原因和串行顺序。
- **L1 可行性评估**：存在独立切片，但本次默认串行。输出并行安全矩阵，不输出执行者分配表。
- **L2 并行准备**：用户明确要求或批准当前实现阶段使用可选并行，且任务确实独立。输出安全矩阵和执行者分配表。

并行组只代表排期候选，不自动启动 Codex 子任务，也不自动推进实现阶段。

## 6. 并行安全矩阵

L1/L2 使用：

```markdown
| 任务 | 组 | 允许修改 | 冲突文件 | 共享依赖 | 契约/SQL/配置影响 | 结论 | 执行方式 |
|---|---|---|---|---|---|---|---|
```

结论只使用“可并行”“需串行”“先锁契约”；执行方式只使用“并行”“串行”“准备并行”。

必须串行的典型情况：

- 修改同一 Java 文件、Service 主链或测试基类；
- 修改同一 Mapper XML、SQL 文件或表结构；
- 修改同一配置、缓存 key 或消息契约；
- Provider/Consumer 或请求/响应口径尚未固定；
- 一个任务的输出是另一个任务的编译或测试前置。

测试数据、样例和测试骨架可以准备并行，但最终通过结论必须等待实现完成。

## 7. L2 执行者分配

只有 L2 才输出：

```markdown
| 执行者 | 任务 | 允许修改 | 禁止修改 | 只读参考 | 依赖 | 合并顺序 | 精确验证命令 | 预期信号 |
|---|---|---|---|---|---|---|---|---|
```

分配规则：

- 允许修改优先使用精确文件；目录级权限只用于唯一命名空间下的新增文件；
- 两个执行者的文件写集不能重叠；
- 冲突文件、共享接口、SQL、配置和其他执行者写集必须进入禁止修改；
- 新增 DTO、枚举、Mapper 和测试类预留唯一名称或路径；
- 合并顺序从基础契约到主链、入口和最终验证；
- 每个执行者有局部验证，但主上下文仍执行整体复核。

## 8. 接口、SQL、风险与测试映射

- 每个接口映射到实现它的功能任务，契约验证写进该任务完成标准；
- 每个 SQL 变更映射 SQL 文件、迁移脚本及实体/Mapper/Repository 等持久化代码任务，人工执行和回滚操作进入非编码交接；
- 每个 Redis/MQ/ES/配置变更映射到实际配置或运行时代码任务；
- 每个旧链路副作用映射到实现防护任务，并在完成标准中写回归信号；
- 每个发布风险进入非编码交接，记录监控、灰度、停止条件或回滚检查，不分配 Txx。

测试执行和测试报告不能生成 Txx。每个功能任务写清场景、命令、预期信号、失败信号和覆盖风险。测试代码默认并入功能任务；只有用户明确要求，或已确认 `Dxx` 明确要求新增/修改测试代码时才规划测试资产并记录来源。测试代码声明与预计修改文件必须一致。独立测试任务只允许真正可跨模块复用的测试基础设施，并写清至少两个复用方。

## 9. 用户纠正和上游回写

发现任务需要改变需求、代码结论或设计时，不在 `03-tasks.md` 里自行改口径：

- 范围/验收改变，回写需求；
- 代码事实改变，回写调研；
- 接口/SQL/状态/发布改变，回写方案。

上游重新校验后再更新覆盖矩阵和任务状态。

## 10. 完成检查

- 覆盖矩阵没有遗漏或无来源任务；
- 每个 Txx 至少引用一个核心 Dxx，且每个核心 Dxx 都被覆盖；
- 关键路径、阻塞点和解除条件清楚；
- 每个任务有精确文件范围、完成标准、精确验证命令和预期信号；
- L0/L1/L2 与实际复杂度一致；
- 同文件、Mapper XML、SQL、配置和契约没有被错误标为并行；
- L2 的允许修改不重叠，禁止修改、合并顺序和验证完整；
- 接口、SQL 文件、缓存/MQ、风险防护和测试代码都有编码任务承接；
- 人工 SQL、环境操作、测试执行、发布和回滚只进入非编码交接；
- `03-tasks.md` 是唯一实施计划，不创建平行 `plan.md`。
