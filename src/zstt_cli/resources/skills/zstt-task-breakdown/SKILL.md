# ZSTT Task Breakdown

## 定位

把 `02-design.md` 变成可以逐项执行的仓库编码计划。`Txx` 只表示会产生仓库改动的编码任务；人工 SQL、环境操作、联调协调、测试执行、测试报告、发布、灰度、监控和回滚只进入非编码交接事项，不分配 `Txx`。这里只拆 full 正式需求；quick 的简短执行计划由实现阶段写入实现记录。

仅当用户明确指定本 Skill 时执行。结束后可以推荐 `$zstt-implementation`，但不得自动执行推荐的下一阶段。

## 开始前

1. 运行 `python .zstt-kit/runtime/rule_resolver.py resolve --skill zstt-task-breakdown`。
2. 以 UTF-8 完整读取解析结果中每个规则的 `path`，记录 `rulesetVersion`、`rulesetFingerprint`、规则 ID 和选择原因。解析失败或规则缺失时停止，并执行 `zstt check --here`。
3. 完整读取本阶段 `references/advanced-playbook.md`。
4. 读取 `00-requirement.md`、`01-research.md`、`02-design.md` 和被主方案索引的辅助附件，建立覆盖矩阵；只为已确认的 DTO、数据访问、事务、并发、抽象或 DDD 任务追加对应上下文并重新解析。
5. 用户显式给出的需求目录优先；未给目录时运行 `current --repo-root <业务仓库>`，仅接受当前 Git 分支上的唯一未完成需求。0 个或多个候选时运行 `list --repo-root <业务仓库>` 展示候选并要求用户选择，禁止按日期猜测。
6. 运行 `python .zstt-kit/runtime/workflow_cli.py prepare-stage --stage task_breakdown --feature-dir <需求目录>`，重新校验需求、调研和方案。
7. 发现方案缺少代码落点、接口契约、数据设计或验证策略时，停止拆分并回到方案阶段修正。

## 拆分规则

每个任务必须包含：

- 唯一任务 ID 和清晰目标；
- 来源依据：至少一个 `02-design.md`“代码改动落点”中的已确认 `Dxx`；需求条目、`Cxx` 和附件只能作为补充来源；
- 实际写入的 Git 项目或仓库；跨项目任务必须拆开；
- 预期文件、模块、接口、SQL 或配置范围；
- 前置依赖、后续依赖和执行顺序；
- 实现要点与明确不做事项；
- 完成标准，包括代码结果、测试代码策略、精确验证命令、预期信号和失败信号；
- 风险、阻塞状态和可否并行。

任务粒度应让实现者能在一个连续上下文中完成和验证，不按 Controller/Service/Mapper 机械切成无法独立闭环的小片段。

## 可追溯性

- `03-tasks.md` 的每个 Txx 至少引用一个已确认核心 `Dxx`；不能只引用需求、`Cxx`、接口明细或 SQL 附件。
- `02-design.md`“代码改动落点”中的每个 `Dxx` 都必须被至少一个合理 Txx 承接。
- 接口、SQL 文件、状态、兼容、迁移、配置和测试代码策略必须映射到具体编码任务；测试执行、发布和回滚等非编码要求映射到交接事项。
- 没有任务承接的核心改动是覆盖缺口；没有核心 `Dxx` 的任务是范围扩张。
- 不重新定义需求或技术方案。发现冲突时先修正上游权威产物。

## 测试与非编码事项

- 测试执行和测试报告不拆 Txx；每个功能任务在完成标准中写入最小验证。
- 测试代码默认并入对应功能任务，不单独拆分。只有用户明确要求，或已确认 `Dxx` 明确要求新增/修改测试代码时，才规划测试类、测试桩、Fixture 或数据构造，并记录来源。
- 测试代码声明必须与预计修改文件一致：默认不新增时文件范围不能出现测试资产；设计或用户授权新增时必须列出具体测试文件或符号。
- 独立测试任务只允许测试基座、共享 Fixture、通用数据工厂或契约测试工具等真正可复用的仓库能力，且必须写清至少两个具体复用方或跨模块复用范围。
- 人工 DDL、数据回填、Nacos/环境操作、联调协调、发布、灰度、监控和回滚保留在“非编码交接事项”，不能作为 Txx 或编码任务依赖。

## 并行判断

先判断 L0/L1/L2 并行等级。首版不自动启动 Codex 子任务；L2 只在用户明确要求或批准当前阶段可选并行时准备执行者分配，且必须保证 Java 文件、Mapper XML、配置、SQL 和接口契约写集不重叠。

## 状态与完成边界

- `ready`、`pending`、`blocked` 描述任务的执行就绪度，不直接等同于任务计划是否完整。
- 缺少上游接口/SQL/状态决策、来源依据、文件落点、完成标准或验证信号，属于计划完整性 P0；停止拆分、保持 `status: draft`，回写对应上游，不用猜测性 `Txx` 填空。
- 任务边界、输出、责任方、解除条件和重新验证动作均已确定，只因外部执行条件未满足时，可保留为 `blocked`；其依赖任务记为 `pending`，传导阻塞引用同一根因，不重复计数。
- 完成前校验依赖图：任务 ID 唯一、依赖均指向已定义任务、每条边有原因且图中无环；循环依赖或悬空引用属于计划完整性 P0，先修正任务边界或上游方案。
- 覆盖无缺口、每个任务定义完整、依赖图和执行顺序无冲突且 P0 为 0 时，计划可以完成，不要求所有任务都为 `ready`；但必须列明当前可执行集合及禁止提前执行的 `pending/blocked` 集合。
- 当前可执行集合只包含直接与传递前置均满足、且不依赖 `pending/blocked` 输出的 `ready` 任务；单独执行会造成接口、Schema、配置或消息契约半完成状态的任务必须与其闭环组一起等待。
- 新生成计划中，引用尚未完成 Txx 的任务必须为 `pending`；`ready` 任务不能依赖当前仍未完成的 Txx。`blocked` 只用于外部执行条件，必须在阻塞表中登记根因、责任方、解除条件和复验动作。

## 完成门禁

1. 按 `ZSTT_TASK_SCHEMA_VERSION` 写入 `03-tasks.md` 的覆盖矩阵、任务总览、任务详情、依赖边、当前可执行集合、文件范围、验证命令和非编码交接信息。
2. 存在计划完整性 P0 时保持 `status: draft`，记录缺口、权威回写位置和重新进入条件；不运行完成命令，下一步只推荐需要修正的上游阶段。
3. 满足计划完成条件后才设 `status: completed`，更新真实问题数量并运行 `complete-stage --stage task_breakdown`。
4. 完成命令失败时立即停止，将 frontmatter 恢复为 `draft`，记录失败原因和重试条件；不得手改 `meta.json` 或宣称计划完成。
5. 只有完成命令成功后，才输出关键路径、任务数、当前可执行集合、阻塞集合和产物路径，并把 `$zstt-implementation` 作为固定下一阶段推荐。若用户希望在编码前横向复核四份上游产物，同时说明可显式调用只读的 `$zstt-artifact-analysis`；它不是固定阶段，不得自动执行，也不得替代任务完成门禁。

## 禁止事项

- 不单独创建 `plan.md`；`03-tasks.md` 就是可执行实施计划。
- 不生成空泛的“修改 Service”“补测试”任务。
- 不生成发布、回滚、人工 DDL、环境操作、联调协调、测试执行或测试报告 Txx。
- 不让需求条目、`Cxx` 或附件绕过已确认核心 `Dxx` 直接产生编码任务。
- 不提前修改代码或生成实现记录。
