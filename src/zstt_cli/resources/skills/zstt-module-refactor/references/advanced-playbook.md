## 1. 范围与真实证据

从用户指定模块开始，不因相邻代码“不够漂亮”扩大范围。先记录入口、内部协作者、最终数据源或计算点、关键参数和全部可观察副作用。

### 1.1 真实调用链

至少追到：

```text
入口 -> 编排 -> 规则/计算 -> 数据访问或远程依赖 -> 持久化/响应/事件
```

对 Controller、Handler、Job、Listener、MQ 消费者、定时任务和回调分别确认入口语义。只看接口名、方法名或搜索片段不能证明真实链路。

### 1.2 Guard 与真实依赖

把入口判空、历史 guard、权限检查与最终业务输入分开记录。字段只有实际参与查询条件、计算公式、持久化、路由、授权或外部契约时，才能认定为真实依赖。

若准备删除一个限制，优先验证最小闭环：失败点、下游调用、最终 fetch/calculation 点、实际参数。没有证据时不增加替代字段、fallback 或跨实体映射。

### 1.3 状态所有权和运行通道

区分：

- 数据库持久化事实；
- Redis/cache 运行状态；
- 内存状态、定时器和延迟任务；
- MQ 事件、WebSocket 推送和 after-commit 动作；
- 派生 DTO、统计结果和外部通知。

不能把不同生命周期的数据笼统写成“同一数据源”。聚合和映射必须从同一实体范围闭环派生，除非代码、Schema、查询或契约证明范围一致。

## 2. 行为基线

重构前在记录中建立行为矩阵：

| 行为面 | 当前事实 | 证据位置 | 必须保持 | 验证方式 |
|---|---|---|---|---|
| 公共接口 | 请求、响应、错误码 | Controller/契约 | 是/否 | MVC/API 测试 |
| 数据结果 | 查询条件、计算公式 | SQL/方法 | 是/否 | 单测/SQL |
| 副作用 | DB、RPC、MQ、缓存 | 调用链 | 是/否 | 集成/Mock |
| 安全 | 权限、校验、敏感数据 | Guard/配置 | 是/否 | 权限测试 |
| 时序 | 事务、锁、重试、通知 | 运行链路 | 是/否 | 并发/时序测试 |

现有测试不足时，优先增加 characterization test 锁定当前输入输出和副作用。难以自动化时保存请求响应样例、SQL 结果、日志或可复现命令，但不能把静态阅读当成运行验证。

## 3. 审阅路径

| 路径 | 适用条件 | 是否等待审批 | 允许内容 |
|---|---|---|---|
| Fast path | 单一窄范围、无契约/数据/事务/时序变化 | 通常不需要额外等待 | 局部职责整理和可直接验证的结构调整 |
| Plan review | 多文件、职责拆分、新抽象、并发/性能/资源治理 | 必须 | 用户批准的行为保持型计划 |
| Behavior change | 任一可观察行为可能变化 | 必须 | 仅批准后的行为变化部分 |

以下变化默认属于 Behavior change，而不是普通性能重构：

- 修改锁等待、持有范围或所有权；
- 修改超时、重试次数、退避和失败降级；
- 改变事务边界、提交顺序或 after-commit 时机；
- 删除或新增权限、校验、异常或兼容分支；
- 改变查询范围、计算结果、外部调用次数或消息时序。

## 4. 重构计划质量

计划至少包含：

- 目标及当前维护成本；
- 入口、真实调用链、最终数据源/计算点和关键参数；
- Guard 与真实业务依赖结论；
- 拟修改文件、只读参考和明确不改范围；
- 每一步修改及其具体理由；
- 公共契约、数据范围、异常、事务和时序的保持依据；
- 修改前后的同基线验证命令；
- 真正影响范围、行为或验证策略的不确定点。

“按 Clean Code 优化”“引入 DDD”“拆得更优雅”不是理由。每一步必须对应当前可见的混合职责、重复规则、依赖泄漏、测试困难、性能风险或可靠性问题。

## 5. 性能、并发与可靠性

### 5.1 性能

只处理有代码或运行证据的问题：N+1、循环 RPC/API、重复计算、重复序列化、无界集合、过量临时对象、阻塞初始化或已定位热点。先记录当前调用次数、数据规模或性能信号，再修改并用同口径复测。

禁止把循环单查换成另一种 N+1，也不得在没有一致性证据时引入缓存。

### 5.2 并发和锁

明确锁键、获取顺序、范围、所有权、可重入假设、等待时间、中断语义、线程安全、共享状态可见性、失败释放和重试窗口。去重锁编排可以是结构重构；改变锁结果或通知时机必须走行为变更审批。

### 5.3 内存、GC 和资源

检查线程池、定时器、监听器、文件、流、连接、缓存和集合的创建、容量、关闭与释放。可在保持生命周期语义的前提下使用 try-with-resources、finally 清理、容量上限或移除不必要分配；任何可能丢数据、提前关闭或改变可见时机的调整先审批。

### 5.4 可靠性和安全

吞中断、无限重试、重试风暴、超时误用、资源泄漏和敏感信息处理不当必须有具体位置和失败条件。若修复会改变错误、重试、权限、持久化或外部可见行为，分离为业务逻辑变更提案。

## 6. 设计模式与 DDD

只在代码已出现真实压力时使用：

- Strategy：存在多个可互换且独立变化的算法或策略；
- Template Method：主骨架稳定、步骤存在受控变化；
- Factory：创建规则复杂、分散或重复；
- Adapter：外部协议形状泄漏到业务层；
- Specification：领域谓词需要组合、复用和独立测试。

DDD 只用于把真实业务规则放回合适所有者、让应用服务聚焦编排。不要为术语新增 Aggregate、Repository、Domain Event、Value Object 或通用基础层。

## 7. 小步实施与偏差门禁

每一步形成闭环：

1. 确认对应计划项和失败/保护信号；
2. 做最小 cohesive edit（内聚修改）；
3. 运行最近的聚焦验证；
4. 检查行为矩阵和 diff；
5. 更新同一重构记录后再继续。

出现以下情况立即停止：

- 需要修改计划外模块或公共契约；
- 真实代码推翻原行为基线；
- 查询、计算、权限、异常、事务、并发或外部副作用可能变化；
- 验证失败且根因不是简单机械错误；
- 用户已有改动与计划写集冲突。

只有用户明确要求或批准、任务写集独立且主上下文建立文件锁时，才可使用 Codex 子任务。子任务不得修改 `.zstt/meta.json`、自动推进流程或执行 commit/push/merge/deploy。

## 8. 等价验证

修改前后使用同一组命令、数据和断言。按风险组合：

- 单元测试、characterization test；
- Controller/MVC、序列化和 Jackson 绑定测试；
- Repository/Mapper SQL 和数据范围测试；
- RPC/MQ/缓存/事务集成测试；
- 并发、锁、定时器、资源释放和性能基准；
- 编译、静态检查和人工调用链复核。

验证报告写命令、退出码、关键输出、通过/失败/未执行和剩余风险。Maven 的 smart-doc 若绑定早期生命周期且目标仅是业务验证，按项目约束使用 `-Dsmart-doc.phase=verify`。

最终 diff 必须确认：修改都来自计划、没有 N+1、没有注释丢失、没有范围外格式化、没有覆盖用户改动、没有未解释的新抽象。

## 9. ZSTT 产物与固定流程边界

独立重构记录写入 `.zstt/refactors/`；关联需求时写入 `<feature-dir>/auxiliary/refactors/`。同一次重构始终更新一个文件，计划、审批、执行和验证共享同一权威记录。

本 Skill 不修改 `.zstt/meta.json`，不占用固定阶段编号。若重构改变了当前需求的实际实现，最终只推荐用户决定是否重新执行 `$zstt-code-review` 或 `$zstt-test-verify`，不得自动调用。

## 10. 交付质量标准

只有满足以下条件才可声明完成：

- 入口、调用链、最终数据源/计算点和关键参数可反查；
- 修改范围与不改范围明确；
- 每个重要修改都有当前证据和理由；
- 行为不变声明列出具体保持项，不写空泛“逻辑不变”；
- 性能/并发/资源改动有基线、保持边界和复测证据；
- 所需审批有明确记录，未批准部分没有实现；
- 验证结果真实，未验证项和剩余风险可执行。
