# ZSTT 能力探测与降级协议

## 1. 原则

能力探测的目的不是展示工具，而是确认当前阶段可以取得什么证据。只探测当前任务确实需要的能力；不要安装工具、猜测工具存在，也不要因为某个增强工具不可用而跳过阶段职责。

每次使用增强能力都要同时定义：

- **增强路径**：工具可用、输入完整且结果可验证时如何使用；
- **标准降级**：工具不可用、结果不完整或权限不足时如何继续；
- **证据边界**：降级后哪些事实仍能证明，哪些只能标为推断或未知；
- **停止条件**：缺失能力何时会使关键事实无法闭环并形成 P0。

## 2. 探测顺序

1. 根据当前阶段和输入列出需要的能力，不做全环境扫描。
2. 检查当前会话暴露的工具、MCP、连接器、仓库和运行环境。
3. 用只读、低成本动作验证工具真的可用，不把工具名称存在等同于调用成功。
4. 记录探测结果、实际使用方式、失败原因和标准降级路径。
5. 对关键结论标记证据等级和证据置信度。

## 3. 能力矩阵

| 能力 | 增强路径 | 标准降级 |
|---|---|---|
| 远程仓库 MCP | 远程只读搜索、读取文件和定位符号；记录仓库、分支或提交 | 使用用户提供的本地 checkout；没有 checkout 时列出所需仓库和最小补充材料 |
| CodeGraph 或代码索引 | 查询入口、调用方、被调用方和跨模块关系；先检查目标项目和索引新鲜度 | 使用 `rg`、Git、构建文件和逐层源码阅读重建调用链 |
| PDF、网页、图片和办公文档读取 | 用对应读取能力提取文字、表格、流程和图示关系 | 读取可访问文本，记录不可读范围，请求用户补充关键页面或文本，不猜测图中内容 |
| Codex 子任务 | 对写集独立的实现任务或只读专项审查并行处理 | 主上下文串行执行，保持相同检查清单和验证步骤 |
| API、token 和测试环境 | 在不暴露凭据的前提下执行接口、主链路和环境验证 | 运行本地编译、单测、静态契约检查，明确环境未验证范围 |

## 4. 工具不可用时的处理

- 工具不可用不是成功证据，也不自动等于业务失败。
- 先执行标准降级，再判断证据是否足以支持当前阶段结论。
- 静态源码能证明结构和参数流向，但不能自动证明运行配置、动态 Bean、远程数据、消息状态或真实权限。
- 如果降级路径仍不能证明接口口径、数据身份、权限、核心状态或验收结果，把问题保留为 P0 或明确的开放风险。
- 不增加 fallback 业务逻辑来补偿分析工具缺失。

## 5. 可选并行能力

并行是当前阶段内部的可选增强，不是自动串行工作流：

- 只读调研和专项 Review 可以按互相独立的检查面并行；
- 实现任务只有在文件写集、接口契约、SQL、配置和验证方式互不冲突时才可并行；
- 主上下文必须复核子任务的文件、证据、diff 和测试结果；
- 子任务完成不得自动调用下一阶段 Skill，也不得直接推进 `meta.json`；
- 并行不可用或不安全时走串行标准降级。

## 6. 阶段记录格式

在当前主产物的工具或证据章节记录：

```markdown
| 能力 | 探测结果 | 实际路径 | 失败/降级原因 | 可证明范围 | 证据置信度 |
|---|---|---|---|---|---|
| CodeGraph | 不可用 | rg + 本地源码 | 当前会话未提供索引 | 静态调用链 | 中 |
```

不要记录 token、Cookie、密码、完整 Authorization 头或其他敏感值。只记录凭据是否存在、作用域是否满足和验证结论。
