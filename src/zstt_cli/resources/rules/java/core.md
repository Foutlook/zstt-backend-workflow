# Java 后端核心规则

## 适用范围

修改或评审 Java 业务代码、接口、任务、配置和测试时使用。项目约束（例如 `AGENTS.md`）、用户要求和已经证明的局部契约优先于本规则。

## 强约束

- 每一处改动都必须能追溯到当前需求、任务、评审问题或已批准的重构计划。
- 先定位直接失败点，再追踪真实调用链、最终查询/计算/赋值点和真正影响结果的参数。
- Guard 条件只决定是否继续执行，不自动等于真实业务依赖。
- 不增加未经代码、Schema、查询或接口契约证明的替代字段、fallback 或新分支。
- 保持当前模块的局部一致性；不要为了统一个人风格改写无关历史代码。
- public 方法优先展示校验、读取、计算、写入、通知和返回等业务顺序。
- 复杂链式调用、非显然计算、复用值或调试关键值才提取局部变量；简单 getter、常量、一层调用和清晰返回保持直接。

## 例子

错误判断：`chapterId == null` 出现在入口判空，所以 `chapterId` 一定是后续查询的核心参数。

正确做法：继续追到最终 Mapper/RPC 调用。如果最终只使用 `ptIds` 查询，且 `chapterId` 只参与历史 Guard，应优先评估移除错误限制，而不是增加 `chapterId` 的推测性 fallback。
