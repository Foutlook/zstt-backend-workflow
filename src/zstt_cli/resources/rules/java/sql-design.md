# Java 后端 SQL 设计约束

## 适用范围

技术方案、实现或评审涉及 MySQL、Mapper SQL、查询语义、DML、DDL、索引、约束或数据迁移时应用。SQL 必须来源于已确认需求和真实代码/Schema 证据，不能用经验补造项目事实。

## 最小设计顺序

1. 证明能否不改数据库，通过现有事实、计算或已有查询完成。
2. 不能时优先复用已有表和字段。
3. 仍不足时只给已有表增加当前闭环必需的最少字段或索引。
4. 只有职责、生命周期或一致性边界确实独立时才新建表。

稳定可推导字段默认不落库。不得为“以后可能”、排查方便、单次使用或未知扩展预留表、字段、索引、状态、布尔标志、计数、`ext_json` 或平行数据源。冗余数据必须说明写入方、同步时机、不一致风险、修复和回滚。

## 表与公共字段

先读取同模块已有表、Entity、Mapper、Schema 或迁移脚本，沿用真实命名、类型、默认值、时间更新方式、逻辑删除值和索引风格。无可靠参考时，默认检查以下公共字段：

- `id`
- `create_user`
- `create_time`
- `modify_user`
- `modify_time`
- `is_delete`

缺省或替换公共字段必须说明表生命周期和项目依据。系统流水、Outbox、幂等、临时或只追加表可以例外，但必须说明写入、更新/删除、清理归档和审计策略。

`user_id`、`tenant_id`、`version`、`status`、`remark`、`ext_json`、`deleted_at` 不是通用公共字段。只有需求、可信身份、租户隔离、乐观锁、状态机或生命周期证据成立时才加入；学生、教师、操作者和创建人使用准确业务语义，不能都折叠成含糊的 `user_id`。

## 精确 SQL 与索引

- 提供接近最终实现的精确 `SELECT/INSERT/UPDATE/DELETE/DDL`，不能用省略条件的伪 SQL 或字段清单代替。
- 明确 JOIN、过滤、分组、排序、分页、逻辑删除、租户/机构/权限范围、更新条件和预计影响行数。
- 每个索引对应真实 `WHERE`、`JOIN` 或 `ORDER BY`，检查联合索引最左前缀、选择性、重复索引和写放大。
- 唯一约束只表达真实业务唯一性；并发去重还要说明冲突处理和返回语义。
- 事务围绕一致性边界设计，不把无依据的慢远程调用放入事务；写清 DB、缓存和 MQ 的提交顺序、幂等与补偿。

生产 MySQL DDL 写明表/字段注释、主键、必要唯一约束和索引，并沿用项目引擎、字符集和排序规则。不得把 H2、SQLite 或测试容器的兼容 DDL 当作生产设计。

## 迁移与风险

新增、删除、重命名、类型/长度/字符集/非空/默认值变化、主键或唯一约束变化都要评估：

- 存量数据量、脏数据和回填范围；
- 锁表、重建索引、在线 DDL 和热点表风险；
- 新旧应用版本、双读/双写和发布顺序；
- 批次、限速、校验、失败重试和停止条件；
- 应用回滚后的字段、索引、新数据和兼容读处理。

缺少会改变正确性或发布安全的数据库版本、数据规模或运行基线时，形成 P0；可逆调优参数可以作为带验证和回退条件的 P1/P2。

## 用户确认门禁

SQL 设计属于技术方案阶段，但必须在代码落点、完整发布方案和任务交接前确认。新增或修改 SQL 语义时，把精确语句写入 `auxiliary/sql-design.sql`，使用运行时 SQL Gate 锁定第 7 节和附件指纹。用户未明确确认、确认来源不可追溯或指纹已失效时，不得完成技术方案或进入任务拆分。
