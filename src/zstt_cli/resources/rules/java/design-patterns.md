# 设计模式决策规则

设计模式是候选解法，不是完成指标。先证明问题，再选择最小模式；没有适用压力时明确记录“不适用”。

| 模式 | 适用证据 | 不应使用 | 例子 |
|---|---|---|---|
| Strategy（策略） | 同一业务目标存在多个可替换算法，选择条件明确 | 只有一个实现或分支稳定且简单 | 按考试类型选择不同计分算法 |
| Factory（工厂） | 创建过程复杂，调用方不应依赖具体构造细节 | 只是为了包一层 `new` | 根据渠道配置构造带不同依赖的支付客户端 |
| Adapter（适配器） | 外部或历史接口不能直接修改，需要隔离协议差异 | 内部接口本就可统一修改 | 把旧 RPC 返回转换为当前领域输入 |
| Template Method（模板方法） | 流程骨架稳定，少数步骤由子类变化 | 需要组合或运行时替换，继承会绑死职责 | 多类导入任务共享校验、落库、通知骨架 |
| Specification（规格） | 业务规则需要组合、复用并独立测试 | 简单一次性判断 | 组合“可报名且未过期且有权限”的条件 |
| State（状态） | 状态转换复杂且每个状态行为明显不同 | 简单枚举加少量分支即可表达 | 订单状态分别控制取消、退款和发货动作 |

## 决策输出

记录问题证据、候选模式、未采用方案、行为边界、引入成本和验证方式。不得为了“使用了设计模式”增加无业务价值的层级。
