# DDD（领域驱动设计）决策规则

## 适用条件

DDD 构件只用于已经存在稳定业务语言、清晰一致性边界和跨用例复用规则的模块。不要把包名调整或类名加上 Domain 当成领域建模。

## 决策检查

- 领域术语是否由需求、代码和团队共同使用，而不是临时发明。
- 聚合根是否真正承担一致性边界，外部修改是否必须经过它。
- Entity（实体）与 Value Object（值对象）的身份和生命周期是否有代码或数据证据。
- Domain Service（领域服务）是否承载跨实体的领域规则，而不是替代 Application Service（应用服务）编排。
- Repository（仓储）抽象是否围绕聚合读写，而不是给每张表机械包装一层。

## 例子

订单及订单项必须在同一事务中维护金额一致性，且所有修改都通过订单完成，可以把订单视作聚合根。仅因为 Service 文件过长就创建 Aggregate、Domain Service 和 Repository，不构成充分理由。
