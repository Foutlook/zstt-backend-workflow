# 抽象决策规则

## 适用条件

只有出现可证明的变化轴、重复业务规则、职责边界冲突或替换需求时，才考虑新抽象。文件数量、类很长或“看起来不优雅”本身不是充分证据。

## 决策步骤

1. 写清当前重复或耦合造成的具体失败、变更成本或测试困难。
2. 找到至少两个真实使用点，或一个已经确认的近期替换点。
3. 明确稳定部分和变化部分，并验证抽象不会隐藏事务、数据源或异常语义。
4. 比较“不抽象”“局部提取”“新增接口/策略”等候选方案。
5. 记录采用或不采用的理由；“不适用”是有效结论。

## 禁止条件

- 只有一个简单使用点，且没有真实变化压力。
- 为未来可能需求提前增加接口、工厂、注册表或配置层。
- 抽象后需要在多层之间跳转才能理解同一条简单业务链。
- 用抽象掩盖来源不一致、异常分歧或职责尚未澄清。

## 例子

两个支付渠道已经存在不同签名、请求和错误映射，并且调用方需要统一重试边界，可以考虑 `PaymentChannel` 接口。只有一个渠道、第二个渠道尚未确认时，保留直接实现通常更合适。
